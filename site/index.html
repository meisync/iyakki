IYAKKI: an operating system built for AI agents

A small, memory-safe operating system written in Rust and WebAssembly, built around an AI assistant that is allowed to do things: safely, visibly and only with your permission.

Alpha (0.1.0-alpha.2, 2026-11-10). A preview for developers and testers, not for production. The installer erases the whole drive you pick. Many features are partial (902 of 1381 rows in the feature matrix; on average 88% is written and 55% is proven, see the progress page) and data formats are not promised to stay stable. Read the known issues first.

What it is

Today an AI assistant is usually a chat box inside someone else's operating system. It can talk, but anything it does (read a file, call an API, run a command) is either impossible or happens with whatever power the program around it has. IYAKKI turns that around: the operating system is built for the agent. The project's aim is to show that an assistant can be useful on a computer (plan your week, read your documents, run kubectl or aws, try a Python program in a container, play music) without being trusted blindly.

Who it is for

  • Developers and testers who want to try an assistant that works under a permission model, on their own machine and with the models they choose (Ollama on the network, or a cloud provider with their own key in an encrypted vault).
  • People who care about auditability. The code is Apache-2.0 and the dependencies are permissive; the project keeps a tested boundary between its own code and the base operating system.
  • Not for production, and not for a machine holding data you cannot lose, while it is alpha.

Why it is different

One permission model

Each person has a role (administrator, operator, user, guest) and a policy: which apps, folders, network hosts, tools and how many tokens. The assistant can never do more than the person it works for.

Risky things ask first

Reading is free. Writing a file, calling an API, running a program or starting a container pauses for Allow once, Allow for this session, or Deny. No answer means deny. Every run is recorded in a tamper-evident ledger.

Untrusted code is sandboxed

Plugins, tools and model-generated code run in WebAssembly (wasmtime) with a fuel budget, a memory cap and capability tokens, or in a limited container.

Yours to run

It talks only to the models you connect. Nothing is sent anywhere you did not configure. One program boots from a USB stick, runs in a virtual machine, as a desktop window, or as a container.

Built in-house, permissively licensed

The editor, browser engine, archive unpacking, Markdown and more are written by the project, so the whole stays Apache-2.0 and small enough to audit.

Key features, by group

After signing in you get a launcher of tiles, sorted into groups. Each tile is an app, locked or unlocked by your role. Status per feature is on the progress page; this is the overview from the README.

Ask and create

  • CHAT with an agent mode: tools, each risky call asks first
  • RAG: search your documents with citations
  • SKILLS, CALENDAR, TALES (story teller), VOICE, LAB

Build

  • AI IDE: editor, terminal, feature board, Kubernetes view, approved Deploy flow
  • GIT, FLOWS (workflows), K8S, EDIT, CLI, MCP, RUNS (history of every agent run)

Media

  • BROWSER: in-house engine, plus an optional full WebKit engine
  • RADIO, MEDIA, CAMERA

Data

  • DATA: open large CSV/TSV/JSON-lines tables
  • DASH: read-only dashboards over Prometheus, Elasticsearch/OpenSearch, ClickHouse and DuckDB
  • USAGE: token use per model

Devices and system

  • SYSTEM, DISKS, NET SCAN, MESH, USERS (roles, limits, audit log), STORE
  • Bluetooth written in-house; encrypted home folders; lock screen

Where it runs

  • Desktop window on Linux
  • USB stick on a PC or Mac
  • QEMU virtual machine
  • Browser front end, Docker, K3s

Marked experimental or alpha in the project's own documents: the wake phrase of the My IYAKKI voice session (experimental, off by default), the Connect a client feature and its window program (experimental), and Linux programs in a sandbox (alpha, untried on a device).

What has been tried on real hardware

From the release notes: the alpha.2 USB image booted on four real computers (a Mac mini 2018, a MacBook Pro 14,1, an HP laptop and a Lenovo laptop), and most of what was tried on real hardware was tried on the Mac mini. Bluetooth pairing, phone sound and tether were tried on the MacBook Pro 14,1. Everything else in the changelog is checked by tests and fakes only; the known issues say what is unproven. Secure Boot is verified in QEMU only on most machines.

How to try it

  1. Download the latest alpha from the GitHub releases and verify the checksums and signatures that come with it.
  2. Follow the install guide: a desktop window on Linux (./run.sh window, needs the Rust toolchain), a USB stick, or a virtual machine.
  3. Then the quickstart. Chat needs a model: Settings, then Models.

The USB installer erases the drive you choose. Do not use it on a machine that holds anything you cannot lose.
