# Where IYAKKI ends and the base OS begins

**IYAKKI** is the code in `crates/` plus the files we add under `dist/buildroot/` (config, overlay, scripts).
**The base OS** is everything we do not write: the Linux kernel, the Buildroot-built userland (BusyBox, kmod,
iproute2, wpa_supplicant, alsa-utils, e2fsprogs, CA certificates), the bootloader (GRUB, later shim) and
firmware. Keeping the line sharp is what lets us change either side without breaking the other, keeps our code
Apache-2.0, and keeps the attack surface small.

## Rules

1. **One direction.** IYAKKI depends on the base OS through the interfaces listed here. The base OS knows
   nothing about IYAKKI internals: it starts `iyakki` as PID 1, passes kernel command-line options, and our files
   live in `/etc/iyakki` and `/var/lib/iyakki`.
2. **Only four kinds of interface:** (A) the kernel ABI (syscalls, `/proc`, `/sys`, `/dev`, ioctls); (B) named
   base programs started as separate processes with fixed arguments and **never through a shell**; (C) kernel
   command-line options; (D) files we own. Anything else is a boundary violation.
3. **No patches to upstream.** The kernel is a stock version plus a config fragment
   (`dist/buildroot/board/iyakki/linux.fragment`). Buildroot is used unmodified through an external tree
   (`dist/buildroot`). We do not fork or patch base programs. If the base lacks something, first change
   configuration, then add a separate optional package; patching comes last, and not silently. **Kernel patches carried,
   Mac image variant only** (`configs/iyakki_mac.fragment`, `BR2_GLOBAL_PATCH_DIR`, folder
   `board/iyakki/patches/linux/6.12.112/`): `0001-drm-i915-skl-keep-the-firmware-cdclk-while-pipes-are-on.patch` (IYAKKI's
   own: i915 on Skylake..Coffee Lake keeps the firmware's display clock instead of turning every screen off to lower it; Mac
   mini 2018, `docs/MAC-HARDWARE.md`); and three pinned GPL-2.0 backports for T2 MacBooks, each naming its source and commit
   in its header: `0002-HID-apple-touch-bar-backlight-and-keyboard-mode-backport.patch` (the Touch Bar drivers
   hid-appletb-kbd and hid-appletb-bl, upstream since 6.15, files from v6.18), `0003-Input-bcm5974-add-support-for-the-T2-Macs.patch`
   (t2linux: the internal trackpad) and `0004-drm-amd-pm-fix-boot-of-the-Radeon-Pro-5300M-in-MacBookPro16-1.patch` (t2linux:
   only that GPU). The default images run the stock kernel plus only the Secure Boot patch below; `crates/iyakki-core/tests/boot_menu.rs` checks both.
   **One kernel patch on every x86-64 image** (folder `board/iyakki/patches-sb/linux/6.12.112/`, `BR2_GLOBAL_PATCH_DIR` of
   `configs/iyakki_x86_64_defconfig`): `0001-x86-lock-down-the-kernel-when-booted-with-UEFI-Secure-Boot.patch` (about 20 lines; the stock
   6.12 kernel has the lockdown LSM and reads the firmware's Secure Boot state but never locks itself down, the step Debian, Fedora and
   Ubuntu carry as a patch by David Howells and Matthew Garrett; rewritten against 6.12.112, GPL-2.0, text in its header). With Secure
   Boot off it changes nothing; with it on, unsigned modules, /dev/mem and kexec are refused (`docs/SECURE-BOOT.md`). **Two more patches, to an out-of-tree module, not to the kernel:** the Mac variant's optional package
   `dist/buildroot/package/apple-bce` (t2linux apple-bce, GPL-2.0: sound and internal USB of T2 Macs) carries
   `0001-apple-bce-work-with-one-MSI-vector.patch` (the BCE gets one MSI vector on a kernel without interrupt remapping) and
   `0002-aaudio-report-periods-from-a-work-item.patch` (no sleeping in the completion handler's spinlock at the end of a
   sound). Both were tried on a Mac mini 2018 (`docs/MAC-HARDWARE.md` section 6).
4. **GPL stays at arm's length.** Base programs are only executed, never linked, so IYAKKI remains Apache-2.0
   (see `LICENSING.md`).
5. **Every touchpoint is listed below and enforced.** `crates/iyakki-core/tests/boundary.rs` fails when non-test
   code outside a listed file starts a process or makes a system-level libc call, and when a listed file no
   longer needs its row. To touch the base OS from a new place: add the row (with the reason) in the same change.
6. **Containers.** `iyakki` also runs in Docker and K3s without the base OS pieces. Code that needs a real boot
   (mounting, driver loading, rebooting) must only run when IYAKKI is PID 1 on a real boot (`boot.rs`), never in a container.
7. **Prefer the kernel ABI to programs.** Each program in table B is a candidate to replace with direct syscalls
   when that is simple and safe (noted per row).

8. **The base OS is replaceable.** Because the interface is this short and listed, a person can swap the base OS for
   another one: a different Linux distribution (Alpine, Debian, Ubuntu, a Yocto or Buildroot image of their own), a
   different kernel build, or a container host. What the replacement must offer is exactly tables A to D: the Linux
   kernel ABI we call, the named ordinary programs (all common on any distribution), the boot options if IYAKKI is PID 1,
   and a place for `/etc/iyakki` and `/var/lib/iyakki`. A kernel that is not Linux would need the files in table A
   ported; that table is the porting list. Nothing outside these tables depends on the base OS, and the test above keeps
   it that way. Only the Buildroot image and a Linux desktop have been tried so far (`F-PKG-14` tracks the others).

## B2. Listeners we open

IYAKKI opens a network listener in four places, none by default: the web front end (`iyakki web`, `iyakki.web`; HTTPS, sign-in), the
**developer-mode listener** (`crates/iyakki-remote/src/devserver.rs`, docs/DEVELOPER-MODE.md: TLS on TCP 7979 by default, all addresses,
opened only while an administrator has switched developer mode on in Settings and closed within two seconds when it goes off or its
automatic switch-off time passes; pairing with a one-time code, then every request signed by a paired ed25519 key; no process is started
and no new program is used), the per-run tool socket of an external coding agent (a local socket), and the **browser voice helper** (`crates/iyakki-agent/src/voicehelper.rs`):
`127.0.0.1` only, a random port, started by a button (Settings → Voice, the TALES chip), a one-time link token, a session secret, `Host` and
`Origin` checked, one tab at a time, closed when the tab closes, goes silent for 45 s, does not open the link within two minutes, or the
person presses Disconnect. Only the text of the pieces being read goes to the tab; nothing leaves the machine through it.

The **sign-in relay page** (`crates/iyakki-remote/src/relay.rs`, policy in `crates/iyakki-agent/src/extagent/relay.rs`) is a sixth: while the sign-in
of Claude Code waits for a code to be pasted, a phone can send it to the device. It is answered on the web front end's own port when that
runs; otherwise a TLS listener on a random port (the web front end's certificate) is opened for the length of the login and closed with it
(Cancel, success, failure, leaving the dialog, or 15 minutes). Only `/login/<128-bit one-time token>` exists, only private and link-local
addresses are served (loopback and public addresses get nothing, not even a TLS handshake on the own listener), a text body up to 8 KiB, 20 requests
a minute per address, and the code goes to the sign-in dialog and from there to the vendor program; only "login relay used" is logged.

**Indic voices** (`crates/iyakki-agent/src/indic/`, Settings → Indic voices) add **no process and no listener** to IYAKKI. They make outbound HTTP requests only to addresses an administrator set: the voice server (the text of one piece at a time, as JSON; default `http://127.0.0.1:8189`, run by the person with `dist/tts-indic/server.py` or deployed as the `indic-tts` platform service) and, after a confirmation card that names the host and the size, the bundle address (three pinned files per language, checked by SHA-256). The Kubernetes service reuses the existing `podman`/`docker build` and `kubectl apply` steps of `wsexec.rs`.

## C. Kernel command-line options we read

`iyakki.selftest` (`1`, `persist1`, `persist2`), `iyakki.shell` (`0` disables the shell), `iyakki.hwcheck` (`1` starts
the hardware check), `iyakki.ssh` (`1` starts the SSH server for diagnostics; key login only), `iyakki.web` (`1`, a port, `host:port` or `http:port` serves the desktop to browsers; also `IYAKKI_WEB` in a container), `iyakki.splash` (`N` keeps the boot screen up for at least N seconds), `iyakki.hostname` (a valid host name; overrides `system.conf` and locks Settings, Host name), `iyakki.data` (`ram` ignores the data volume), `iyakki.zram` (`off`, `auto`, a size, `N%`, `<size>,<algorithm>`), `iyakki.swappiness`, `iyakki.swapfile` (`off` or a size) and `iyakki.zswap` (`on`/`off`) for memory (`docs/ZRAM-AND-INSTALL.md`), `iyakki.selftest=memory|installhere` with `iyakki.testinstall` and `iyakki.testtemplate` (test only: `qemu-memory-install-test.sh`), `iyakki.webtest` (test only, `qemu-web-test.sh`: an address to open in the full web engine at boot; use with `iyakki.shell=0`), `iyakki.disk` (self-test disk), `iyakki.env`
(force environment detection). Boot entries live in `dist/buildroot/board/iyakki/grub.cfg`.

## D. Files and directories IYAKKI owns

`/etc/iyakki/` (`net.conf`, `ai.conf`, `mcp.json`, read-only config shipped in the image overlay),
`/var/lib/iyakki/` (`system.conf`: memory and host-name settings written by Settings and the installer, `settings.json`: also the time zone and time server chosen in Settings, Time, `swapfile`: the optional swap file, `k3s-dev/`: the dev cluster's program, data, kubeconfig and log, `devmode/`: developer mode's state, paired computer keys, activity log and app logs, accounts, the devices seen on the network (`devices.json`), settings, vaults, knowledge base, chats, runs, skills, `store/` (the app store: what is installed, cached catalogs, licences, the revocation list), audit log, the browser front end's `tls/` certificate, `ollama/` models and log, `wifi.json` (the WiFi networks joined from Settings); this is the only
place IYAKKI writes; it is the IYAKKI-DATA volume when one exists), `/run/iyakki*` (scratch), `/var/log/iyakki-boot.log` (the boot screen's story: when the framebuffer appeared, its geometry, why the splash stopped). IYAKKI never edits other
base files.
