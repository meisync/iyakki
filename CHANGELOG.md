# Changelog

All notable changes to IYAKKI are written here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)
and the project uses [Semantic Versioning](https://semver.org/). Every 0.x release can change anything; the alpha series
(`0.1.0-alpha.N`) additionally promises nothing about stability, data formats or upgrade paths (see
[SECURITY.md](SECURITY.md) and [KNOWN-ISSUES.md](KNOWN-ISSUES.md)).

The rows behind each item, and the tests that prove them, are in [FEATURES.md](FEATURES.md). What is only partly true is
listed in [KNOWN-ISSUES.md](KNOWN-ISSUES.md); an item below is not a promise that it was tried on real hardware.

## [Unreleased]

### Added

- **Browser speed: scrolling and video measured on a Mac, Smooth pages, half the llvmpipe threads, tile-only drawing** (F-BROW-57, F-BROW-58, [docs/BROWSER-SPEED.md](docs/BROWSER-SPEED.md), "Interactive performance"): page loads were never slow (2.6 to 5.3 s); scrolling and video were. A new kit (`dist/webview/interactive-timing.sh` and the `probe` example's `measure` and `bench` steps) records pictures a second, gaps, CPU per process and per thread, memory and a YouTube player's dropped frames on a real device. On a MacBook Pro (no Intel driver in the image) the engine's software GL threads are the cost: a 60 fps 720p YouTube clip showed 6 to 8 pictures a second and dropped 61 to 80 % of its frames. **Settings -> Browser -> Smooth pages** (off by default; key `m`) draws the page at half the width and height and stretches it: 27 pictures a second and no dropped frames on that clip. The engine now gets half the logical CPUs for llvmpipe (`LP_NUM_THREADS`; the `web-tuning` file takes several words: `cpu:4 lp:2 gstgl:off nice:5 fps:60`), which stopped the dropped frames (0 in 4 of 4 runs against 428 to 564 in 4) and used 29 % less CPU scrolling Wikipedia. The shell paints only the page rectangle when only the engine's picture changed (a whole scene is still drawn every 100 ms and on any other change) and no longer fills the page area white first. Found and not fixed: one web-process thread burns a core during any video because the T2 audio device runs with a one-frame period. Not measured: the shell's own draw time with a live tile (needs a signed-in session). Needs a new `iyakki` in the image; the helper's opt-in `IYAKKI_WEBVIEW_NICE` needs the next web image build.

- **Assistant skills for build and deploy to k3s** (F-IDE-19, [docs/AI-IDE.md](docs/AI-IDE.md), [docs/K3S-DEV.md](docs/K3S-DEV.md)): two new built-in skills, `k3s-build-and-deploy` (the short happy path for "build this and deploy it": cluster named first, test image, runtime image, load, manifest, apply, verify, rollback, multi-cluster rules, failure table, definition of done) and `k3s-dockerfile-patterns` (a multi-stage non-root Dockerfile for Node, Python, Go, Rust, Java, C#, PHP and static sites). The build-and-deploy skill is pinned with the broad k3s skill for deploy requests, and up to three skills are pinned now (was two).

- **Screen saver and screen off** (F-SCRN-01 to F-SCRN-05, [docs/SCREEN-SAVER.md](docs/SCREEN-SAVER.md)): after the idle time each person chooses (standard 10 minutes; Settings -> Display & sound -> Screen saver) the screen shows the IYAKKI logo drifting, breathing and glowing slowly on black (or the logo with the clock, a small dim logo for OLED, a breathing logo), and after 10 more minutes turns off; or turns off directly, or does nothing. A laptop dims first and, on the battery, every time is halved. The screen stays on while music, the radio or a tale plays, while an approval, an alarm, the low-battery card or the drive banner is up (and for anything that calls `Shell::inhibit_screen_off`). Any input wakes it, and the first key or click only wakes (a stray click presses nothing). Screen off paints black once, stops drawing, puts the backlight to 0 (the exact old value is kept in a RAM file and put back, also after a crash and restart) and powers the framebuffer down (`FBIOBLANK`); the Touch Bar strip follows; the window and remote screens only show black. The saver redraws only the rectangle the logo left and the one it moved to, 15 frames a second (8 on battery, 4 remote). The sign-in screen has its own times (saver after 5 minutes, off 10 later), set by an administrator. Tested with fake clocks, folders and framebuffer calls, and in pictures; **not yet seen on a real panel**. Not built: a lock (there is no lock screen), a photo slideshow, a starfield, a start-now chord, and browser video as a reason to keep the screen on.

- **Crash forensics: the kernel log survives a crash** (F-SYS-04, F-SYS-05, F-BOOT-33, [docs/TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md)): after a crash or power cut the kernel log was gone, so nothing showed why. From the moment the data volume is mounted (normal and lean boot) the kernel log is appended to `/var/lib/iyakki/log/kmsg-<boot-id>.log` (at most 2 s late, at once for errors and crash words; a bounded queue and its own thread, nothing written while the drive-loss watcher is not Healthy; last 3 boots and every crash file kept, 8 MB per boot, 64 MB in all). A session that did not end through power-off or reboot is noticed at the next start: its log is kept as a crash file, the audit log gets `system.unclean-shutdown`, and Settings -> Overview says "The last session ended unexpectedly" with a button to the new Settings -> Last session log (last 200 lines, "I have seen it"). `iyakki log kernel [--previous] [--crash]` and `iyakki log sessions`. Every boot entry now has `panic=20` (restart 20 s after a kernel panic). Tested with fakes only; needs a new image to take effect.

- **Pointer shapes on the framebuffer** (F-SHELL-47, [docs/TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md)): on bare metal the pointer was always the arrow, so links showed no hand. The framebuffer display loop now draws the shape the shell asks for (arrow, hand, I-beam, wait, crosshair, move, not allowed, resize both ways, grab, help; hidden when the page hides it) with in-house sprites, each with a hotspot (fingertip, centre), scaled like the arrow, and repaints just the pointer's rectangle when the shape changes under a still mouse. Tested with fakes only; needs an image build and a stick write before it shows on the Mac.

- **T2 Mac sound for the browser, and capture made safe** (F-SND-05, F-SND-06, [docs/MAC-HARDWARE.md](docs/MAC-HARDWARE.md), [docs/TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md)): YouTube had no sound or noise on a MacBookPro16,2. Measured: ALSA's `plug` plays 24/32/16/12 kHz audio at the wrong speed on the T2 device and cannot take 32-bit float at 44.1 kHz. The web engine now plays through its own `iyakkiweb` PCM (never converts the rate, integer formats), apple-bce patch 0003 gives real periods and refuses capture unless a module parameter allows it (opening the loopback crashed a Mac), the Voice tile hides the T2 microphones, and idle web pages release the sound device when something else needs it. Not yet tried on a Mac after the change (needs an image build).

- **Touch Bar strip, display only, and a careful bring-up** (F-KBD-12, F-KBD-13, F-KBD-14, [docs/TOUCH-BAR.md](docs/TOUCH-BAR.md), [docs/MAC-HARDWARE.md](docs/MAC-HARDWARE.md)): on a T2 MacBook IYAKKI draws its own 2170 x 60 strip on the Touch Bar from user space (usbfs; the wire format re-derived from the description of the kernel's `appletbdrm.c`, no GPL code copied): System (volume, brightness, keyboard light, play/pause, clock), Recent (last six apps), AI (Claude Code state, Chat, Ask, Stop, Approve/Deny, IDE Run/Save) and App (up to six items the focused app offers) strips, redrawn only on change at most ten times a second, dark when idle, only the name before sign-in; Settings -> Keyboard has Touch Bar mode (default, strip, keys, off), strips and picture flip. Any failure or "off" hands the T2's function keys back at once (modes 0 to 3 and the Fn toggle are unchanged). The boot-time -110 retry no longer loops 2-then-1 three times: a device with a configuration is left alone, round 1 writes 2 then 1, round 2 resets that one device once and writes 1, round 3 writes 1, then it gives up. The strip finds the configuration that holds the display from the device's descriptors and, because on a MacBookPro16,2 configuration 1 has only the HID keys, switches to it once per boot (`USBDEVFS_SETCONFIGURATION`, same-device checks, no retry, one way back if it fails), then opens the display; the firmware keys' mode file is found again after the drivers rebind. A Touch Bar touch panel is never a pointer on the main screen. **Fakes only, never run on the device; display only until the kernel exposes the bar's touch panel (not in 6.12).**

- **Publish into the private store you just deployed** (F-APPS-51, [docs/STORE.md](docs/STORE.md) section 17.1, [docs/TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md)): the IDE could not publish into a private store deployed from the same device because the deploy never added it to the STORE (no catalog source, no pinned key, no target), so the Publish form offered only Deploy and Export. The form now lists such a store first, shows its catalog key fingerprint on one card and "Add it and publish" adds it with the key pinned (the Settings step, refusing a changed key), chooses it as the target and shows the review; the vault token is found for `localhost`, `127.0.0.1`, the device address, slashes and `/catalog.json`; a store whose pod does not answer is explained with the K8S tile as the next step; "Deploy a new private store" says "already deployed"; every publish failure names what happened and what to do; the assistant's `store_publish` and `tile_ship` take `add_deployed_store` (the fingerprint) so one approval card adds and publishes. Tested with fakes and a loopback store server only; not yet run on the MacBookPro16,2.

- **Blocking ads and trackers, and what is known about the full engine's speed** (F-BROW-52 to F-BROW-56, [docs/CONTENT-BLOCKING.md](docs/CONTENT-BLOCKING.md), [docs/BROWSER-SPEED.md](docs/BROWSER-SPEED.md) "Full engine (WPE)", LICENSING.md item 19): an in-house filter-list engine (EasyList and uBlock network rules, simple hiding rules; indexed matching with no regular-expression engine, about 2.5 microseconds a request with the real lists) blocks requests before they are sent in the reader, and writes the same rules as WebKit content-blocker JSON that the full-engine helper loads through WebKit's filter store. Settings -> Browser -> Ads and trackers (on by default, nothing blocked until a list is downloaded): the lists are third-party data, never shipped, fetched at a click or added by address or file, with licence, age and SHA-256 shown and a weekly refresh; in the browser "N blocked" in the bottom bar, B lists what was blocked, A allows the site, and a blocked page shows which rule did it. **Not measured, not promised:** the MacBook was offline, so nothing was timed in the full engine; the WPE helper change was never compiled or run against WebKit; the effect on YouTube video ads is not claimed. Found from the build: no Intel GPU driver in Mesa on the web images (WPE paints through llvmpipe), JIT on, libsoup HTTP/2 yes, Brotli and WOFF2 no; `web-profile/web-tuning` lets an administrator try Skia CPU raster; rebuild options are written down, nothing was rebuilt.
- **Browser speed and memory** (F-BROW-51, F-BROW-36, [docs/BROWSER-SPEED.md](docs/BROWSER-SPEED.md)): measured first (`cargo run --release -p iyakki-js --example browser_timing -- URL`, and `dist/webview/page-timing.sh` for the full engine on a device). YouTube and Google open in the full web engine on the web images, which this change does not touch; for the built-in reader a preload scanner fetches a page's style sheets, scripts and pictures together (bbc.com/news with scripts 2.7 s to 1.8 s, 6.5 s to 2.7 s on a slower link; pages without scripts unchanged because they are bound by style and layout CPU), connection limits (6 per host, 32 overall, urgent first), a bigger HTTP connection pool and a DNS cache, and a new page cache: memory tier plus disk tier sized from free memory and disk (shrinks under memory pressure), revalidation with ETag and Last-Modified, stale copy when offline, static files cached even with cookies, never `no-store`, `private`, cookie-setting or cookie-varying answers, one cache folder per person. Settings -> Browser -> Speed and memory: cache size Auto, Large or Small, numbers in use, Clear cache. Not done: any change to the full engine, HTTP/2, style and layout speed.
- **Surviving the loss of the boot drive** (F-LOSS-01 to F-LOSS-06, [docs/STORAGE-LOSS.md](docs/STORAGE-LOSS.md)): seen once on a MacBookPro16,2 running from a Samsung T7 over USB-C: the drive vanished for 0.6 s, came back as a new device and `/var/lib/iyakki` and `/home` stayed mounted on the dead one (I/O errors everywhere). A watcher thread (mount table, `/sys/block`, a 1-byte fsync'd probe with a bounded wait, no process spawned) reports Healthy, Lost, Errors, ReadOnly or Reattachable; a red card on every screen says it in plain words (cannot be dismissed, can be minimised; Reconnect now, Restart, Check the drive); apps say "the IYAKKI drive is not available" instead of a bare I/O error; events go to a RAM ring that is written to the audit log after the drive is back; when the very same filesystem (UUID, label) returns on a new node and is steady for 3 s it is mounted on a staging folder (journal replay), the stale mounts are detached lazily, `/home` is bound again and the k3s dev cluster is stopped and started around it; never fsck; `iyakki storage status|reattach`. USB runtime power management is set to `on` for the boot drive, Settings, Storage shows the link speed, port and hub with warnings, and an optional Compatible USB mode (no UAS, GRUB entry and a switch) is off by default. **Tested with fakes only; the real disconnect path was seen once in a log and has not been reproduced.**

- **Developer mode over ONE cable between two computers** (F-DEV-10 to F-DEV-12, F-NET-14, F-FW-12, [docs/DEVELOPER-MODE.md](docs/DEVELOPER-MODE.md) section 10): `iyakki dev usb` and Settings -> Developer mode -> Connect over USB-C (key `u`) check, pair, authorize and measure a Thunderbolt 3/4 or USB4 link (or a host-to-host USB bridge cable, or a USB gadget port) with seven steps that say in plain words what to do; `thunderbolt0` and bridge-cable interfaces come up by themselves with an IPv4 link-local address (ARP probing written here) and a peer beacon, with no DHCP; the firewall treats them as a direct-link zone (developer mode, beacon and ping only, switch "Allow more"); kernel options `USB4_NET`, `USB_NET_PLUSB`, `USB_NET_NET1080`, `USB_NET_CDC_SUBSET` (aarch64 also USB gadget) need a kernel rebuild. Two ordinary PCs cannot talk over a plain USB-C cable: the docs say so. Tested with fakes only, never with two real machines.
- **Laptop battery and charging** (F-BATT-01 to F-BATT-05, [docs/BATTERY.md](docs/BATTERY.md)): the top bar of a laptop shows a battery drawn by IYAKKI (green, amber under 20 %, red under 10 %, a bolt while charging, a plug when the adapter is in and the battery is full or protecting itself, a question mark when unknown) with the percentage; a click or F4 opens a popup with the bar, the status in plain words, time left or until full, health, cycles, technology, maker, model and the adapter; Settings, Battery (laptops only) has the same facts and three switches (percentage in the bar, low-battery warnings, shut down at the critical level, the last for administrators). Messages at 20 % and 10 %, a *Plug in now* card at 5 %, and at 3 % (or the firmware's *critical*) a 30 second countdown card that plugging in or *Cancel shutdown* stops, then a clean shutdown through the existing safe power-off path; it never acts on a machine without battery data, on a 0 or garbled reading, while charging or on the adapter. A desktop, a virtual machine, a Mac mini and a Bluetooth mouse's battery show nothing; two batteries are combined. A laptop whose kernel has no battery driver shows a question mark and *No battery driver: this image needs a newer kernel*. The reading is `/sys/class/power_supply` every 10 s (no program is started; the adapter every second). **Kernel change: `CONFIG_ACPI_BATTERY=y` (and `ACPI_AC`, `POWER_SUPPLY`, `ACPI_SBS`, ...) in `linux.fragment`; arm64 also `BATTERY_SBS` and `BATTERY_BQ27XXX`. The PC, Mac and `hw` images need a kernel rebuild** (a 2020 MacBook Pro showed only the adapter). Tried with made-up `/sys` trees only; nothing was run on a real laptop after the rebuild.

- Allow by host name (looked up by IYAKKI, refreshed every 5 minutes and when the network changes, last good answer kept), IP address, IP range or CIDR, with ports, protocol, interface, a note and an end time; presets for SSH, remote desktop, shared folders, Kubernetes, DNS service; `iyakki.ssh=1` keeps SSH reachable.
- A changed ruleset waits 60 seconds for Keep and is taken back by itself; emergency ways out: Settings, the Devices list, `iyakki firewall off`, `iyakki.firewall=off`. A failure to apply says NOT PROTECTED; a kernel without nf_tables says "Firewall not available in this kernel".
- Settings -> Firewall (administrators): rules table, draft, Apply / Keep / Revert, presets, import and export as JSON, the count and the last 50 blocked attempts. The Shared folders page says when the firewall keeps other devices out of a share.
- Tested with fakes and, in a private network namespace, against a real kernel; **not tried on a device or booted**.

**Install next to another system (F-INST-05 to F-INST-13, `docs/INSTALLER.md`)**
- A partition planner: reads a disk (GPT or MBR, filesystems by signature, labels, mount state, free-space gaps) and turns "whole disk", "free space only", "custom sizes" or "use these partitions" into a plan table (create / format / delete / keep, with sizes and what is lost) before anything is written. Plan as JSON (`--plan-file`), `--dry-run`, and a digest the writer re-checks.
- Rules in code and tests: nothing mounted is touched; the disk the system runs from needs the typed confirmation; partitions not in the plan are never written (fingerprinted before and after, protective MBR identical); no shrinking (free space must exist); 1 MiB alignment; GPT backup at the true end; 4096-byte sectors; MBR 4-slot limit; BOOT size read from the image.
- Dual boot: keep the other system's EFI System Partition and add only `EFI/IYAKKI` (in-house FAT32 appender) plus an "IYAKKI" UEFI boot entry appended to `BootOrder` (written through `efivarfs`).
- Install modes in three places: terminal pages (`iyakki-usb --plan`, `iyakki install --plan`), the boot-menu entry **IYAKKI - Install to a disk** (`iyakki.install=1`, the installer on the text console, the booted stick excluded), and a window installer (`iyakki-installer`, pkexec for the privileged writer, image from a file or an https link with `.sha256` check). A stick made with `--table gpt` is now accepted as the install source.
- Tested on disk image files only (sparse temp files; the writer refuses anything but a regular file in a test build). **Not run against a real disk, not booted, the window not clicked through**; Windows/macOS hosts and legacy-BIOS boot of a shared disk are planned.

**Remote desktop in a browser, much less bandwidth (F-WEB-09 to F-WEB-13, `docs/REMOTE-PROTOCOL.md`)**
- Protocol version 2: 64x64 tile damage tracking (an unchanged screen sends nothing), per-tile codecs (solid, palette, filtered raw, lossy YC for photo-like tiles) deflated together and decoded by the browser itself, lossy tiles sent again exactly when the picture goes still. Text and interface tiles are always exact. No H.264, no GPL code.
- Flow control: at most two unacknowledged pictures, nothing queued, newest picture wins; levels Lossless, Balanced, Low bandwidth, Very low (halved picture) chosen from the measured link, a manual choice and a data saver in the page's display settings, Ctrl+Alt+S statistics.
- The page decodes in a worker where it can, has touch gestures, an on-screen keyboard button and fullscreen. Old pages (no `hello`) keep working with version 1 PNG pieces. Measured numbers in the protocol document.
- Tested over loopback and a simulated link, and the decoder under node; **not tried in a real browser, on a phone or over a real slow link**.

**Model host on your network (F-MODELHOST-01 to F-MODELHOST-04, F-APPLE-01, `docs/MAC-MODEL-HOST.md`)**
- Use the GPU of a Mac with Apple Silicon (any M-series, through Metal) or of any other computer on your network: IYAKKI menu → Quick install → *Use a Mac's GPU (Apple Silicon)*, or Settings → Models → *Mac / GPU host* (`H`). IYAKKI installs nothing on that computer; the page shows what you install (Ollama, llama.cpp, MLX-LM: MIT; LM Studio: free but proprietary) with the flags to listen on the network, the security warning and a memory table.
- *Test*: model list, then a tiny streamed chat, with tokens per second and plain messages for refused, no answer, not OpenAI-compatible, 401, malformed JSON and oversized answers. *Add to Models* registers `mac-<nickname>` (key in the vault); several hosts allowed. Only local-network addresses unless you type PUBLIC.
- *Scan this network* (on your click only): the /24 around this machine, four usual ports, short timeouts; lists, never adds.
- *Publish to cluster*: a Service + Endpoints `mac-<nickname>` in `iyakki-ai` so pods call `http://mac-<nickname>:<port>`; *Test from the cluster* runs a small non-root pod through the managed kubectl.
- Tested against fake servers on loopback and a scripted kubectl; **not tried with a real Mac or a real cluster**. The light VM for k3s on macOS stays documented, not built.

**Cloud mode (F-CLOUD-01 to F-CLOUD-05, `docs/CLOUD-MODE.md`)**
- A machine-wide mode (Settings, Cloud mode; Automatic, On, Off; boot parameter `iyakki.mode=cloud|desktop`) for machines with no screen, input, sound or camera: hides MEDIA, RADIO, TALES and CAMERA, the Sound, Display, Keyboard and Bluetooth pages, hardware rows of the Devices popover, the Media player and Mac drivers menu entries, and turns the Fn and media keys off; their shortcuts do nothing and the sound and camera services do not start.
- Automatic turns it on when there is no display, no keyboard or pointer, no sound card, or the image variant says cloud; hardware that exists stays visible. About and Settings say why.
- Tested on made-up machines only; no cloud VM or server was booted.

**Shared folders (F-SHARE-01 to F-SHARE-07, `docs/SHARED-FOLDERS.md`)**
- Settings → *Shared folders*: share a folder of yours over HTTP on the local network (browse, download with Range, optional uploads) or as a small website; also *Share this folder…* in the AI IDE tree and EDIT. Built in (no new program).
- Off until a share is made and started; read-only unless uploads are switched on; one port per share (8081 and up, its own browser origin); secret link (revocable), password (Argon2id), anyone on the local network (typed confirmation) or this machine only; public addresses always refused; expiry of 1 hour, 1 day, 7 days or never; everything stops at sign-out and with *Stop all sharing* (also in the Devices list).
- Safety: paths checked and kept inside the folder (symbolic links out are 404), dotfiles hidden, the system data folder never served, pages and scripts served as downloads in a listing share, limits for connections, headers, slow clients, rate and uploads, audit lines without secrets.
- Tested on 127.0.0.1 only; not tried from real devices. The images have no firewall (the port is open on the chosen interfaces).

**Home layout (F-SHELL-22, F-SHELL-31 to F-SHELL-34)**
- Four built-in sections (Home, Web & Media, Work, System); Settings and the AI IDE are on Home.
- Move a tile to another group (`m`, right-click, or pick it up and click a chip), with a one-step Undo and Reset layout; make, rename, order and delete
  groups of your own (the **+** chip, up to 12); a **…** chip takes the groups that do not fit the width; built-in groups cannot be renamed or deleted.
- A Store app's app.json `group` goes to a matching group, or asks once whether to create it (docs/APP-AUTHORING.md).
- Settings -> Home layout. The layout is per person and changes only where a tile is listed, never what an app may do.

**Git in the AI IDE (alpha.2 item 4; F-GIT-01 to F-GIT-04, `docs/GIT-AND-SSH.md`)**
- *Clone repositories…*: many repositories into one workspace, one address per line with `#branch`, depth and folder per repository, two clones at
  a time as detached jobs, one failure never stops the others, a retry button, `repos` in `.iyakki/project.json` (seen by the assistant and the
  external agents), test and run commands per repository, `@gitea-name/owner/repo` for the platform's Gitea.
- *Repositories…*: state per repository in the tree and a panel, Fetch all, Pull all (fast-forward only, asks first over local changes), typed-name Remove.
- *Settings → Git and SSH keys*: ed25519 keys made in-house or imported (also passphrase-protected ones), kept in the vault; the public half with Copy
  and a QR code; which key or token each git host uses, with a per-workspace override; known hosts with a fingerprint card on first use and a
  refusal when a key changed; every use audited.
- A small in-memory ssh-agent and an askpass helper serve git for the length of a batch: no private key or token is ever a file, an argument or a log line.
- The web and Mac images carry `git`, libcurl and OpenSSH's `ssh` client alone (`/usr/libexec/iyakki/git-ssh`); `repack.sh --graft git` puts them into an
  existing image (about 14.3 MB, 3.4 MB packed). Not yet assembled or booted on a real machine.

## [0.1.0-alpha.1] - 2026-10-19

First public alpha: a preview for developers and testers, not for production or for machines holding data you cannot lose. Everything is
new, so this is the list of what exists, grouped by area. "Tested" means automated tests and QEMU boots; the one real computer used is a
**Mac mini 2018 (Macmini8,1, T2), checked on 2026-10-18/19** (see ALPHA-GATE.md and KNOWN-ISSUES.md). Last full test run on 2026-10-18:
3,845 passed, 0 failed, 59 ignored.

### Added

**Hardware: Mac mini 2018 (the only real machine tried)**
- Boots the install image from a USB SSD through GRUB with a logo menu on UEFI; boot screen with logo, progress and messages; first-boot
  data volume format in 178 ms and a persistent `/home`. GRUB waits 20 to 30 s at the logo today (a side image on the boot partition is planned).
- HDMI audio and the built-in speaker and headphone jack through the out-of-tree `apple-bce` driver; software volume and mute.
- USB webcam through the `uvcvideo` quirk applied at boot; the CAMERA app takes photos, video and passport pictures.
- Not working yet: the Mac's Wi-Fi (BCM4364 needs Apple's firmware copied from macOS) and Bluetooth (needs `brcm/BCM.hcd`). T2 MacBook Pro 2019
  patches and Apple Silicon support are scaffolding only.

**Browser and media (web and macweb images)**
- The full web engine (WPE WebKit) opens Google and YouTube; typing in pages works; YouTube video plays (VP9 + Opus, software rendered).
  H.264/AAC is deliberately not shipped. A media player built on `ffmpeg` (downloaded by Quick install at the user's request), a radio (MP3),
  and the camera app. The media player is not yet confirmed on a real screen.

**Quick install and the dev cluster (tried on the Mac mini)**
- A k3s dev cluster (node Ready), Elasticsearch, DuckDB (Python wheel), Node.js, Python 3.13 (standalone) and `ffmpeg`, all downloaded from

**Added in the last days before the alpha**
