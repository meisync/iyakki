# Known issues in 0.1.0-alpha.1

This is the honest list, written on 2026-10-19. It comes from the "Not verified" and "Known gaps" sections of the README, the "Unverified" notes in
`docs/`, and every row of [FEATURES.md](FEATURES.md) that is not `done` (the full generated list is the appendix at the end).
If something is not here and it does not work, please report it: see [SUPPORT.md](SUPPORT.md).

**The one sentence to remember:** IYAKKI has been run in QEMU, in a desktop window and in containers, and since 2026-10-18 on **one real
computer, a Mac mini 2018 (Macmini8,1, T2)**. It has not been run on any PC, any other Mac, a managed cloud cluster or against most vendors'
live services. **This alpha is a preview for developers and testers.**

## Do not use it for

* **Production, or any machine that holds data you cannot lose.** The installer (`iyakki-usb --install`, and `iyakki install`) erases the
  whole drive you choose. The data volume is **not encrypted** (vaults inside it are).
* Production clusters. The deploy tools refuse profiles that look like production, but the cluster side was exercised against fake
  `kubectl` runners and local K3s (including the dev cluster on the Mac mini), never a managed cluster (EKS/GKE) or a real remote cluster.
* **Secure Boot on real hardware.** Secure Boot (shim + MOK, [docs/SECURE-BOOT.md](docs/SECURE-BOOT.md)) was verified in QEMU with OVMF only (signed
  GRUB, kernel and modules boot, unsigned ones are refused; 17 checks). It was **not tried on any real PC or on a T2 Mac**, and it needs the
  owner's key and its enrolment. Images are signed only when the owner builds with `IYAKKI_SB_KEY`/`IYAKKI_SB_CERT`; otherwise they are
  unsigned and need Secure Boot off. The initial RAM disk is not signed; GRUB 2.12 lacks the 2025 security fixes; driver packs with unsigned
  modules are refused under Secure Boot.
* Anything exposed to the internet. The browser front end speaks HTTPS with a self-made certificate and has had no outside review. The
  in-cluster registry one-click (private store) opens the registry to the network on NodePort 30500 **without a password**.

## Hardware: what was tested

**Tested on real hardware (one machine):** a Mac mini 2018 (Macmini8,1, T2; Intel UHD 630; 32 GB), booting the macweb install image from a USB
SSD (Samsung T7), with an HDMI monitor, Ethernet, a USB keyboard, mouse and webcam, on 2026-10-18/19. What worked there: the stick written
by `iyakki-usb` (GPT, read-back verified), booting through GRUB on UEFI, the boot screen, the data volume and persistent `/home`, HDMI audio
and the built-in speaker and headphone jack (through the out-of-tree `apple-bce` driver), software volume and mute, the USB webcam, the
clock and time zone, the k3s dev cluster and the other Quick install items, Claude Code and GitHub Copilot CLI install and sign-in,
Lemonade on the LAN, and the full web engine (Google, YouTube with VP9 video). Details: [ALPHA-GATE.md](ALPHA-GATE.md) items 46 to 54.

**Expected to work, but untested:** other Intel PCs, laptops and mini PCs (UEFI or BIOS), Intel Macs without a T2 chip, the Mac mini 2014,
other USB cameras, sound devices and drives. `docs/BOOT-TEST.md` is the guide and `iyakki hwreport` is how you tell us what happened.
(F-BOOT-01)

**Not working or not verified, on the Mac mini 2018 and elsewhere:**

* **Wi-Fi of the Mac mini 2018 (Broadcom BCM4364) does not work yet.** It needs Apple's firmware, which IYAKKI never ships. The IYAKKI
  menu, Mac drivers page now installs it at your request: **Download from Apple** (the recovery image of your Mac model, read with 7-Zip),
  or from a folder, a stick or a disk image (the macOS script `dist/drivers/mac-wifi-firmware-from-macos.sh` still works). The file
  names the kernel asks for are verified on the Mac mini, and on 2026-10-21 Apple's recovery download worked and 7-Zip read the image there; **the install and the result have not yet been seen on the Mac**; the recent macOS image has **no Bluetooth patch file for the BCM4364** (the job then tries the other macOS version Apple offers) (a numbered real-device checklist is in `docs/MAC-WIFI-BLUETOOTH-SETUP.md`). Until
  the firmware is installed the Wi-Fi and Bluetooth drivers of a T2 Mac are meant to be held back so the kernel log has no error spam (the first device run showed the blacklist alone did not hold; the module files are now moved aside too, not yet retried). Use Ethernet
  or a USB adapter meanwhile. No Wi-Fi adapter of any kind has associated with a real access point; the join logic is tested with
  stand-ins. The Mac mini 2014's BCM4360 needs Broadcom's non-free `wl` that you build yourself (`dist/drivers/build-wl-pack.sh`); never
  loaded on a real Mac. (F-NET-02, F-DRIVERS-*)
* **Bluetooth does not work.** The Mac mini 2018's BCM4364 has no firmware file in macOS (measured: neither the latest nor the other
  macOS version Apple offers contains a BCM4364 patch file, and there is no legal source), so its controller runs in its ROM state
  (limited): it registers as `hci0` but has no valid address. Settings → Bluetooth shows that (controller, address, powered on/off,
  reason), can power it on and scan for devices for 10 seconds as proof it works; the Bluetooth drivers stay set aside until the
  person presses "Load the Bluetooth driver anyway" (Mac drivers page, Devices) or a Bluetooth driver pack is installed. Pairing
  and audio are not available yet (they need a Bluetooth stack: docs/BETA-PLAN.md). A USB Bluetooth adapter is the reliable option.
  Not yet seen on the Mac: the new page and the scan. Elsewhere: adapter on/off only. (F-NET-11, F-NET-12)
* **The newest image is not confirmed on the Mac.** The fix for a 5.3 s input-device scan stall at boot and the shared sound mixer fix (YouTube
  had no sound while the radio played) are in the newest image but were not tested on the Mac mini.
* **The boot is slow at the start.** GRUB waits 20 to 30 s at the logo (the screen says 'please wait 30 s to 1 min') while the 160 MB initramfs
  is read through the Mac firmware's USB driver; a side image on the boot partition is planned. The first picture of the shell comes about
  9 s after the kernel starts, then the login.
* **T2 MacBook Pro 2019:** keyboard, trackpad and Touch Bar patches are built and compile-checked but were **never booted on a MacBook**.
* **Apple Silicon:** only a VM recipe and Asahi packaging scaffolding. M1 and M2 (M3 limited) could run natively later; M4, M5 and M6 are not
  supported by Asahi yet. The aarch64 image runs as a VM (`docs/APPLE-SILICON.md`).
* **ARM64:** the image boots in QEMU only (software emulation, slow); no ARM64 hardware, cluster or CLI install was tried.
* **Bare-metal PCs:** untested. Touchpads, touch screens and GPUs other than the Mac mini's Intel UHD 630 were never tried; touchpad support
  on bare metal is planned.
* **Microphone and the Mac's own FaceTime camera:** not tested (the USB webcam was).
* **The `hw` image** (firmware blobs) was never booted on a real machine.
* **Display:** bare metal uses the fbdev framebuffer (no DRM/KMS), software rendered and single-threaded. Video in the web engine is
  decoded in software: a 720p YouTube video dropped about 57 of 628 frames, 1080p60 drops more. Very large UI sizes on small screens can
  overflow some pages.
* **Boot time and size:** about 1.6 s to the sign-in screen in QEMU (the Mac mini takes much longer, see above); the spec's 30 MB / 100 ms
  targets are not met (the libre ISO is about 60 MB; the web image about 2 GB).

## Browser and media

* **H.264 and AAC video does not play, on purpose.** They are not shipped (patent policy). TikTok loads but its video does not play.
  YouTube plays VP9 + Opus. Hardware decoding through VA-API is an idea for later. Playback is software-rendered.
* The media player is built on `ffmpeg` (a static build downloaded from the vendor at your request, never shipped). It was tested with fakes and
  with a real file decode, but **not yet confirmed on screen**. The same `ffmpeg` decoded the camera's AVI on the Mac mini.
* The small built-in browser (non-web images) has no video decoding, no canvas, no IndexedDB, no PDF viewer. Chinese, Japanese, Korean and
  emoji text shows as boxes. See `docs/BROWSER-ROADMAP.md`. The full web engine (WPE WebKit) is in the large web and macweb images only; it opened
  Google and YouTube on the Mac mini and in QEMU, but was not exercised across many sites (`docs/BROWSER-AGENT.md`).
* **YouTube video and big pages are slow in the full engine on Macs, and this was measured.** Loading takes 2.6 to 5.3 s; what is slow is
  scrolling and video: on the web and macweb images Mesa has no Intel driver, so WPE composites with llvmpipe on the CPU (a 60 frames a
  second 720p clip: 6 to 8 pictures a second, 61 to 80 % of its frames dropped; 1080p about 2). **Settings -> Browser -> Smooth pages**
  (off by default; half the pixels, softer text) gave 27 pictures a second and no dropped frames on the same clip, and a 24 fps 1080p
  clip played at its own rate; half of the CPU threads for llvmpipe stopped the dropped frames (both need a new `iyakki`, not the image's
  engine). While any video plays one thread of the web process uses a whole core because the T2 audio device runs with a one-frame period
  (`avail_min 1`): not fixed. The real fix, the Intel GPU driver (`WEB_IRIS=1`), is not in any image. The shell's own drawing with a live
  tile was not measured, and the tile-only painting that should speed it up has only been tested, not run on a screen. Brotli and WOFF2
  fonts are still off (`docs/BROWSER-SPEED.md`, "Interactive performance").
* **Ad and tracker blocking** (Settings, Browser): lists are downloaded by the person and are other people's work; the full engine's
  rule loading was never run against a real WPE WebKit and its helper code was not compiled yet; the full engine reports no count of
  blocked requests; about a fifth of the path rules of the real lists do not fit WebKit's limit; YouTube video ads are not promised
  to go (`docs/CONTENT-BLOCKING.md`).
* Radio plays MP3 only.

## Assistant, agents and services

* **Live checks:** Ollama (earlier) and a Lemonade server on the LAN (Mac mini, 2026-10-18/19). OpenAI, Anthropic, Gemini and OpenRouter are
  implemented against their documentation and tested with scripted servers; no live verification without keys. (F-AI-02)
* **Claude Code** (native installer and sign-in) and **GitHub Copilot CLI** (installer and sign-in) were installed and signed in on the Mac mini.
  **Copilot with full tool use is not verified:** bridged mode fixed the handshake bug, but a run with real tool calls and a real sign-in end
  to end has not been done. **Autopilot with external agents** needs 'Allow Auto' in Settings, Agents and was not run end to end. Codex and
  Gemini CLI adapters were tested only against fake CLIs. (docs/EXTERNAL-AGENTS.md)
* **Claude Code's own foreground Bash cannot be switched off by IYAKKI.** The generated instructions tell it to call `mcp__iyakki__job_start` for
  slow work, but the vendor's built-in shell is outside IYAKKI's policy bridge. Treat that as advice. (F-JOBS-04)
* **Developer mode (`iyakki dev ...`)** was tested on loopback only.
* **Tile-app one-step publishing (`tile_ship`)** was tested on loopback only, not against a store deployed on k3s.
* **Private store in the cluster:** the one-click in-cluster registry has tests with fakes only and was not run on the real cluster. It is open
  to the network on NodePort 30500 with no password. The store server itself ran over loopback and once in a local container.
* **Platform services (Gitea, the private store)**, jobs, voice engines and TALES pictures: fakes and scripted stand-ins; never a real cluster,
  speaker or picture model. A real k3s ran on the Mac mini, but these services were not deployed to it. `docs/PLATFORM-SERVICES.md`,
  `docs/JOBS.md`, `docs/VOICE.md` and `docs/STORE.md` end with what was and was not verified.
* **Dashboards:** no real Prometheus/Elasticsearch/ClickHouse server of each kind was used in tests. DuckDB (Python wheel) and Elasticsearch
  were installed by Quick install on the Mac mini; the dashboard connectors were not driven against them. (docs/DASHBOARD.md)
* **Picture generation:** Ollama's image models run only on macOS. **Indic text-to-speech:** the licence of the voice weights is undecided, so
  none is shipped.
* **Voice engines are not shipped** (GPL or voice licences of their own); IYAKKI finds what the computer has, or the browser's voice. (F-VOICE-05..07)
* **TALES picture quality with real models is unjudged.** Small local models mostly cannot draw rich SVG, which is why the built-in cartoon
  composer exists. (F-TALES-06, 13, 15..18)
* **Withdrawing (yanking) a package from a private store does not disable copies already installed.** (F-APPS-40, docs/STORE.md section 13)
* **Approvals:** session grants are for the chat and the IDE chat only; INBOX approvals and Parallel-tasks workers ask every time. (F-ASSIST-40)
* **Audit-log chain:** the race is fixed for one process only; two processes on one `audit.log` can still race, and a chain that already reads
  BROKEN stays BROKEN (start a new log; docs/ADMIN-GUIDE.md). (F-SHELL-01)
* **Several stores and the portal:** the official address is empty ("coming soon") and up to 8 stores can be added. (F-APPSTORE-18, 19)
* **Message box limits:** 20,000 characters in chat, 4000 in the TALES idea box; longer text is cut with a visible notice.
* Many assistant helpers are heuristics with **English-only phrase tables** (refusal retry, stall guard, advice detection, tool-call repair,
  credential guard). Do not paste secrets into the chat; use the vault. Most assistant machinery was driven with scripted models; only some of
  it with a live qwen-class model. "Done needs proof" can be bypassed by editing the board file by hand.

## Accounts, files and security

* **IYAKKI's own accounts only.** IYAKKI accounts are not Linux users; **user files are root-owned** on the data volume (`/home`).
* **Firewall (`docs/FIREWALL.md`).** New incoming connections are blocked by default, outgoing ones are not filtered, forwarding is not touched. Host-name rules are only as trustworthy as the DNS server. The rules and the boot order were tested with fakes and a real kernel in a network namespace, not on a device or together with a running k3s; a machine whose kernel lacks nf_tables says so and is not protected. The firewall page is in Settings (no System tile).
* **The root filesystem is in RAM.** Changes to the system outside `/var/lib/iyakki` and `/home` vanish at reboot.
* The data volume is not encrypted. The browser front end has a self-signed certificate and has had no outside review.
* GitHub Copilot CLI's sign-in token moved into the vault in a later build than the one first tested on the Mac mini.

## Not built yet (stubs and plans)

* **Payments** for paid apps (the Buy button is disabled). (F-APPSTORE-13)
* **The official store root key and a hosted official catalog:** not generated, `official-roots.txt` is empty, `OFFICIAL_STORE_URL` is empty.
  (F-APPSTORE-14, F-APPSTORE-06)
* **Flows:** Thrift nodes can be placed but refuse to run; webhook triggers and the remote runner are not built. (docs/FLOWS.md)
* Encryption of the data volume (F-STORE-05), a read-only compressed system image (F-STORE-06), copy-on-write snapshots (F-WASM-06), an external
  vector store, Bluetooth userland, lazy driver loading through a device broker, a DRM/KMS renderer.
* **Laptop battery:** images built before the kernel change (`CONFIG_ACPI_BATTERY`) have no battery driver, so a laptop shows a question mark and *No battery driver*; the new indicator, warnings and critical shutdown were tried on made-up `/sys` folders only. No power profiles, suspend, charge limits or per-app power use. (F-BATT-01 to F-BATT-05, docs/BATTERY.md)
* **Screen saver and screen off** ([docs/SCREEN-SAVER.md](docs/SCREEN-SAVER.md)): tried with fake clocks, fake `/sys` folders and a fake framebuffer call only, never on a real panel; whether `FBIOBLANK` turns a given monitor off depends on its GPU driver. No lock (no password on waking), no photo slideshow, and a video playing inside the browser does not keep the screen on.
* **Native web views for Chat, Edit, Runs and Settings** and the editor compiled to WebAssembly.
* **Windows and macOS window builds** are not part of this alpha (`docs/MACOS.md` is "written for, not yet tried").

## Install and storage

* Two installers, both erase the whole drive you pick: `iyakki-usb` (writes the stick from another computer; `--all` for internal disks) and
  `iyakki install` / SETTINGS, System, Install to disk (docs/ZRAM-AND-INSTALL.md). `iyakki-usb` wrote and verified the stick for the Mac mini 2018
  (GPT). The on-device installer ran only in QEMU against virtual disks; 4096-byte-sector drives and internal disks of real computers were not
  tried (F-INST-03). Not done: "install next to another system", an encrypted data volume, an installer on the aarch64 image (F-INST-04).
* **DISKS tile** (mount, unmount, eject, partition manager, [docs/DISKS.md](docs/DISKS.md)): written and tested against a made-up machine only (fake `/sys`, `/proc` and mount runner); it has never mounted, ejected or partitioned a real drive. Try the partition manager on a spare USB stick only. The images' kernels lack the NTFS, exFAT, Btrfs, XFS and HFS+ drivers, so those drives are listed but not opened; BitLocker and LUKS cannot be unlocked; exFAT and NTFS formatting and resizing are not supported (F-DISKS-08).
* **zram** (compressed swap) was seen in QEMU only; behaviour under real memory pressure is untested. There is no hibernation.
* The release signing key and the download page are new; the first signed release is this one. Compare the printed public key with the one in
  the README.
* The images in a release are built by `./run.sh build`; an image made before the version bump says `unknown` for the version in About.

## Tests and quality

* **Tests:** the last full `cargo test --workspace` (2026-10-18, evening) had **3,845 passed, 0 failed, 59 ignored**. The ignored tests load live
  websites, call real services or need real hardware; they were run by hand on one machine, not in a pipeline. Later changes were checked with
  focused suites, and a final full run follows before the tag.
* QEMU scenarios: boot (BIOS and UEFI), install, persistence, Secure Boot (17 checks), and the macweb image with Google, Bing and YouTube pages.
* Tests leak temporary folders in `/tmp`; run the suite with `TMPDIR` on a disk (`./run.sh test` and `./run.sh alpha-check` do this).
* Some screens were checked by eye on rendered pictures and in QEMU at four sizes, and a few on the Mac mini's monitor; most not on real displays.
* There is no continuous integration yet; `./run.sh alpha-check` is the substitute.

## Licence notes

* The images contain GPL/LGPL programs as separate executables (Linux, BusyBox, GRUB, ...); whoever redistributes an image must offer their
  source (`legal-info/`). The libre image has no proprietary firmware. Third-party tools (`ffmpeg`, Claude Code, Copilot CLI and others) are
  downloaded from the vendor at the user's request and are never shipped.
  See `docs/LICENSES.md`.
* **Restricted firmware is not in the images** (2026-10-23, [docs/RESTRICTED-FIRMWARE.md](docs/RESTRICTED-FIRMWARE.md)): Qualcomm Bluetooth patch files under `LICENSE.qcom`, PCIe Realtek `rtl_nic`, Broadcom `tigon`/`bnx2`/`bnx2x` and `carl9170-1.fw` are installed by the person at a click (Store, Setup, Hardware) or built into their own image. Until then: the Qualcomm laptop Bluetooth chips do not work, bnx2/bnx2x server NICs and AR9170 USB Wi-Fi sticks do not start, tg3 and r8169 ports work at reduced function. All of it is tested with fakes only: no image was built and nothing was tried on a device; the PCI/USB id tables may miss a board (the folder route and `--force-hardware` cover that).
