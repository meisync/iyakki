# Known issues in 0.1.0-alpha.1

This is the honest list, written on 2026-10-19. It comes from the "Not verified" and "Known gaps" sections of the README, the "Unverified" notes in
`docs/`, and every row of [FEATURES.md](FEATURES.md) that is not `done` (the full generated list is the appendix at the end).
If something is not here and it does not work, please report it: see [SUPPORT.md](SUPPORT.md).

**The one sentence to remember (updated 2026-10-26):** IYAKKI has been run in QEMU, in a desktop window and in containers, and on **three
real computers**: a Mac mini 2018 (Macmini8,1, T2; 2026-10-18/19), a 2020 MacBook Pro with the T2 chip (MacBookPro16,2; from a USB SSD, and its
internal disk booted on 2026-10-24) and **one AMD PC** (it booted; what else worked was not written down, so it counts as untested in detail).
It has not been run on any Intel PC, any NVIDIA PC (an Intel + NVIDIA and an AMD + NVIDIA PC are planned for 2026-10-26; no result is recorded),
any other Mac, a managed cloud cluster or against most vendors' live services. The table is in [docs/HARDWARE.md](docs/HARDWARE.md). **This alpha is a preview for developers and testers.**

## Do not use it for

* KI-001 **Production, or any machine that holds data you cannot lose.** The installer (`iyakki-usb --install`, and `iyakki install`) erases the
  whole drive you choose. The data volume is **not encrypted** (vaults inside it are).
* KI-002 Production clusters. The deploy tools refuse profiles that look like production, but the cluster side was exercised against fake
  `kubectl` runners and local K3s (including the dev cluster on the Mac mini), never a managed cluster (EKS/GKE) or a real remote cluster.
* KI-003 **Secure Boot on real hardware.** Secure Boot (shim + MOK, [docs/SECURE-BOOT.md](docs/SECURE-BOOT.md)) was verified in QEMU with OVMF only (signed
  GRUB, kernel and modules boot, unsigned ones are refused; 17 checks). It was **not tried on any real PC or on a T2 Mac**, and it needs the
  owner's key and its enrolment. Images are signed only when the owner builds with `IYAKKI_SB_KEY`/`IYAKKI_SB_CERT`; otherwise they are
  unsigned and need Secure Boot off. The initial RAM disk is not signed; GRUB 2.12 lacks the 2025 security fixes; driver packs with unsigned
  modules are refused under Secure Boot.
* KI-004 Anything exposed to the internet. The browser front end speaks HTTPS with a self-made certificate and has had no outside review. The
  in-cluster registry one-click (private store) opens the registry to the network on NodePort 30500 **without a password**.
  Fixed in the tree 2026-10-28: `localreg::tests::the_registry_manifest_has_no_network_exposure`, `localreg::tests::an_existing_nodeport_registry_is_converted_to_loopback_and_audited`, `regsetup::tests::applying_over_an_open_nodeport_registry_closes_it_first`, `k3sdev::tests::a_cluster_that_becomes_ready_closes_an_old_open_registry_and_audits_it`; verify on the image: `curl http://<ip>:30500/` must fail from another computer.

* Linux windows / Linux apps on an image (2026-10-29): the first Mac run failed with `linuxapp-init: pivot_root: Invalid argument` because an image's root is the initramfs. Fixed in the tree (enter by mount move and chroot on `rootfs`); proven in QEMU on an initramfs, **not yet run on the Mac**, and `apt` inside the sandbox on an image has never completed. The isolation on `rootfs` is a chroot over a covered mount, not a replaced root (docs/LINUX-APPS.md).

## Hardware: what was tested

**Tested on real hardware, machine 1 of 3:** a Mac mini 2018 (Macmini8,1, T2; Intel UHD 630; 32 GB), booting the macweb install image from a USB
SSD (Samsung T7), with an HDMI monitor, Ethernet, a USB keyboard, mouse and webcam, on 2026-10-18/19. What worked there: the stick written
by `iyakki-usb` (GPT, read-back verified), booting through GRUB on UEFI, the boot screen, the data volume and persistent `/home`, HDMI audio
and the built-in speaker and headphone jack (through the out-of-tree `apple-bce` driver), software volume and mute, the USB webcam, the
clock and time zone, the k3s dev cluster and the other Quick install items, Claude Code and GitHub Copilot CLI install and sign-in,
Lemonade on the LAN, and the full web engine (Google, YouTube with VP9 video). Details: [ALPHA-GATE.md](ALPHA-GATE.md) items 46 to 54.

**Machine 2: a 2020 MacBook Pro with the T2 chip (MacBookPro16,2), owner report, not in `ALPHA-GATE.md`.** Booted from a USB SSD (Samsung T7):
keyboard and trackpad, speaker sound (through `plughw`; the shared mixer is off by default and not run on it), the GPU browser helper, YouTube autoplay and
sound, page fullscreen and the Touch Bar backlight worked. On **2026-10-24 the first install to the internal disk booted**. Still open there: the
IYAKKI-drawn Touch Bar strip never opens (the USB configuration switch falls back), the built-in microphone is off on purpose (capture has hung the
machine), Bluetooth (BCM4364: no patch file exists; fails), upgrading that install, battery (kernel options not yet in an image), sleep, Secure Boot.
**Seen on 2026-10-26/27 (coordinator, through developer mode; no saved diag file):** the macweb image booted from the internal disk, k3s Ready (v1.37.1) and started
again at boot, the internal panel (2560x1600) and a DisplayPort monitor (1920x1080) were driven, Wi-Fi works with Apple's firmware, the built-in camera works, T2 audio works,
developer mode works over Wi-Fi. Built and **not yet verified**: the touch panel on the monitor hub reacts on the wrong display, the camera picker, developer mode blocked
by the device firewall on port 7979, TALES highlight drift inside sentences, the dev cluster after an address change. Per-capability table:
[docs/project/HARDWARE-MATRIX.md](docs/project/HARDWARE-MATRIX.md).
The boot drive (a T7 over USB-C) vanished once for 0.6 s (F-LOSS-01 to F-LOSS-06).

**Machine 3: an AMD PC, owner report only.** It booted. The model, the GPU, and whether sound, network, input and an install worked are **not
recorded anywhere in the repository: untested in detail** until a hardware report is saved (`iyakki hwreport`, [docs/BOOT-TEST.md](docs/BOOT-TEST.md)).

**Planned, no result yet (PC image built 2026-10-26, tests 2026-10-27, QEMU boot only so far):** an Intel + NVIDIA PC and an AMD + NVIDIA PC (the owner reports the AMD one booted; no log). NVIDIA cards run on `nouveau` (Turing and newer) unless the person
installs the vendor driver ([docs/GPU-K3S.md](docs/GPU-K3S.md)).

**Expected to work, but untested:** other Intel PCs, laptops and mini PCs (UEFI or BIOS), Intel Macs without a T2 chip, the Mac mini 2014,
other USB cameras, sound devices and drives. `docs/BOOT-TEST.md` is the guide and `iyakki hwreport` is how you tell us what happened.
(F-BOOT-01)

**Not working or not verified, on the Mac mini 2018 and elsewhere:**

* KI-005 **Wi-Fi of the Mac mini 2018 (Broadcom BCM4364) does not work yet.** It needs Apple's firmware, which IYAKKI never ships. The IYAKKI
  menu, Mac drivers page now installs it at your request: **Download from Apple** (the recovery image of your Mac model, read with 7-Zip),
  or from a folder, a stick or a disk image (the macOS script `dist/drivers/mac-wifi-firmware-from-macos.sh` still works). The file
  names the kernel asks for are verified on the Mac mini, and on 2026-10-21 Apple's recovery download worked and 7-Zip read the image there; **the install and the result have not yet been seen on the Mac**; the recent macOS image has **no Bluetooth patch file for the BCM4364** (the job then tries the other macOS version Apple offers) (a numbered real-device checklist is in `docs/MAC-WIFI-BLUETOOTH-SETUP.md`). Until
  the firmware is installed the Wi-Fi and Bluetooth drivers of a T2 Mac are meant to be held back so the kernel log has no error spam (the first device run showed the blacklist alone did not hold; the module files are now moved aside too, not yet retried). Use Ethernet
  or a USB adapter meanwhile. On the 2020 T2 MacBook Pro the same firmware route worked (Wi-Fi up with addresses by DHCP, 2026-10-26/27, observed through developer mode); on the Mac mini 2018 no
  adapter has associated yet and the run must be repeated there. The Mac mini 2014's BCM4360 needs Broadcom's non-free `wl` that you build yourself (`dist/drivers/build-wl-pack.sh`); never
  loaded on a real Mac. (F-NET-02, F-DRIVERS-*)
* KI-006 **Bluetooth does not work.** The Mac mini 2018's BCM4364 has no firmware file in macOS (measured: neither the latest nor the other
  macOS version Apple offers contains a BCM4364 patch file, and there is no legal source), so its controller runs in its ROM state
  (limited): it registers as `hci0` but has no valid address. Settings → Bluetooth shows that (controller, address, powered on/off,
  reason), can power it on and scan for devices for 10 seconds as proof it works; the Bluetooth drivers stay set aside until the
  person presses "Load the Bluetooth driver anyway" (Mac drivers page, Devices) or a Bluetooth driver pack is installed. Pairing
  and audio are not available yet (they need a Bluetooth stack: docs/BETA-PLAN.md). A USB Bluetooth adapter is the reliable option.
  Not yet seen on the Mac: the new page and the scan. Elsewhere: adapter on/off only. (F-NET-11, F-NET-12)
* KI-007 **The newest image is not confirmed on the Mac.** The fix for a 5.3 s input-device scan stall at boot and the shared sound mixer fix (YouTube
  had no sound while the radio played) are in the newest image but were not tested on the Mac mini.
* KI-008 **The boot is slow at the start.** GRUB waits 20 to 30 s at the logo (the screen says 'please wait 30 s to 1 min') while the 160 MB initramfs
  is read through the Mac firmware's USB driver; a side image on the boot partition is planned. The first picture of the shell comes about
  9 s after the kernel starts, then the login.
* KI-009 **T2 MacBook Pro:** booted (see "Machine 2" above) for the 2020 MacBookPro16,2. The 2019 model and the other T2 MacBooks (2018 to 2020) were not tried.
* KI-010 **Apple Silicon:** the way is a lightweight VM with k3s and a bridge to the model runner (owner decision 2026-10-27); **bare metal is out of scope and not promised**
  (F-BOOT-09, F-DRIVERS-12 and F-DRIVERS-19 are `deprecated`). The VM recipe has never been run on a Mac (`docs/APPLE-SILICON.md`).
* KI-011 **ARM64:** the image boots in QEMU only (software emulation, slow); no ARM64 hardware, cluster or CLI install was tried.
* KI-012 **Bare-metal PCs:** one AMD PC booted (no details recorded); all other PCs are untested. Touchpads, touch screens and GPUs other than the
  Mac mini's Intel UHD 630 (and the MacBook's integrated GPU) were never recorded as tried; touchpad support on bare metal is planned.
* KI-013 **Microphone and the Mac's own FaceTime camera:** on the T2 MacBook Pro (2026-10-26/27, observed through developer mode) the built-in camera works at 640x480 YUYV and an
  external USB microphone works (owner); the built-in microphone of T2 Macs stays off on purpose (capture hung the machine). Fixes built and not yet verified there: the camera
  picker, the touch panel mapping on a second display, developer mode behind the device firewall (port 7979). Not tested on any other machine.
  **Browser microphone (2026-10-28):** on the T2 MacBook the web engine's own ALSA microphone path failed (`Rate doesn't match (requested 44100Hz, get 0Hz)`, then not-negotiated; a page recorded a flat line). Reproduced on a PC: a raw `hw:` capture at a rate the hardware lacks is not-negotiated, `plughw` converts. A new microphone plugin (`libgstiyakkimic.so`) lists the capture streams itself and opens them through `plughw`; the Browser's microphone question has a Microphone chooser that is the same choice as the Voice tile's. Written and tested with fake devices and a PC sound card, **not yet run on the Mac**; the T2 card's microphones also need the `apple_bce` capture switch (`echo 1 > /sys/module/apple_bce/parameters/capture`, off by default), whether `Digital Mic` delivers sound there is unproven, and the engine needs the media-stream rebuild (F-BROW-72). The helper logs one `iyakki-mic:` line per request for the next diagnosis.

## Browser and media

* KI-017 **H.264 and AAC video does not play, on purpose.** They are not shipped (patent policy). TikTok loads but its video does not play.
  YouTube plays VP9 + Opus. Hardware decoding through VA-API is an idea for later. Playback is software-rendered.
* KI-018 The media player is built on `ffmpeg` (a static build downloaded from the vendor at your request, never shipped). It was tested with fakes and
  with a real file decode, but **not yet confirmed on screen**. The same `ffmpeg` decoded the camera's AVI on the Mac mini.
* KI-019 The small built-in browser (non-web images) has no video decoding, no canvas, no IndexedDB, no PDF viewer. Chinese, Japanese, Korean and
  emoji text shows as boxes. See `docs/BROWSER-ROADMAP.md`. The full web engine (WPE WebKit) is in the large web and macweb images only; it opened
  Google and YouTube on the Mac mini and in QEMU, but was not exercised across many sites (`docs/BROWSER-AGENT.md`).
* KI-020 **YouTube video and big pages are slow in the full engine on Macs, and this was measured.** Loading takes 2.6 to 5.3 s; what is slow is
  scrolling and video: on the web and macweb images Mesa has no Intel driver, so WPE composites with llvmpipe on the CPU (a 60 frames a
  second 720p clip: 6 to 8 pictures a second, 61 to 80 % of its frames dropped; 1080p about 2). **Settings -> Browser -> Smooth pages**
  (off by default; half the pixels, softer text) gave 27 pictures a second and no dropped frames on the same clip, and a 24 fps 1080p
  clip played at its own rate; half of the CPU threads for llvmpipe stopped the dropped frames (both need a new `iyakki`, not the image's
  engine). While any video plays one thread of the web process uses a whole core because the T2 audio device runs with a one-frame period
  (`avail_min 1`): not fixed. The real fix, the Intel GPU driver (`WEB_IRIS=1`), is not in any image. The shell's own drawing with a live
  tile was not measured, and the tile-only painting that should speed it up has only been tested, not run on a screen. Brotli and WOFF2
  fonts are still off (`docs/BROWSER-SPEED.md`, "Interactive performance").
* KI-021 **Ad and tracker blocking** (Settings, Browser): lists are downloaded by the person and are other people's work; the full engine's
  rule loading was never run against a real WPE WebKit and its helper code was not compiled yet; the full engine reports no count of
  blocked requests; about a fifth of the path rules of the real lists do not fit WebKit's limit; YouTube video ads are not promised

## SSH tunnels

* **Not tried against a real SSH host.** Everything is tested with a fake client (docs/SSH-TUNNELS.md, "What is verified"). That OpenSSH 10.2 accepts the exact arguments and that its error texts match the mapping is unproven.
* **`-J` (jump hosts) may not work on the images.** OpenSSH starts the jump hop with the `ssh` of its compiled-in path (`/usr/bin/ssh`), which on an image is Dropbear's client; the git-ssh package installs OpenSSH only as `/usr/libexec/iyakki/git-ssh`. A tunnel with a jump chain may fail there until the package sets `_PATH_SSH_PROGRAM`. A single host is not affected.
* **Per-site routing is not built**: the Browser does not choose a tunnel by domain yet (seam: `sshtunnel::SiteRouter`). Open the address shown on the page.
* A host that git also uses loses its trusted-host line when the last tunnel using it is deleted; git then shows the fingerprint again.
* IPv6 literal host names are not accepted in a tunnel; use a name.

* KI-067 **The shell crate's tests needed more than 8 GB in one process** (found 2026-10-28; **fixed 2026-10-28**). Measured cause: not live shells or app threads (a counting allocator showed under 150 MB in use at any time while the process held 1.5 GB after 600 tests) but glibc: each test runs on its own thread, every thread gets a malloc arena, and the arenas keep the pages the test freed, so about 3.5 MB per test stayed resident. Fix: `crates/iyakki-shell/src/testmem.rs` (tests only, Linux glibc; started from `Shell::new` and the `temp_dir` test helper) fixes the mmap threshold at 128 KB so big buffers go back when freed, and a helper thread calls `malloc_trim(0)` twice a second. The whole lib run (`RUST_TEST_THREADS=4`, 8 GB cap, no swap) now peaks at 2.2 GB resident (about 50 minutes) and finishes: 2,503 passed, 0 failed, 33 ignored. Known remainder: tests that log in leave two threads each (`flow-tick`, `flow-assist`, started by the login for the schedule runner) running until the process ends (about 850 threads at the end, small); stopping them on `Shell` drop would need a stop signal in `iyakki-agent` flows (not done). The tests that start the fake web helper build it on first use; run them from the cargo-built test binary, not from a copy.
* KI-069 **Browser microphone: a page's `getUserMedia` never answers on the Mac, and the cause is not proven** (found 2026-10-28; **open**). Seen on a plain test page served from k3s (`http://127.0.0.1:<nodeport>/`, secure origin) with `audio: true` and with explicit flags, and on three recorder sites; the first test on one site did record. Evidence: the mic plugin opens `plughw:1,0` each time; the engine log (diagnosis switch `/tmp/iyakki-dev/gst-debug`) shows the capturer start, `audiornnoise` missing (a warning), then 3 ms later an audio output on `autoaudiosink` that fails (`Could not open device for playback in stereo mode`, `sink not negotiated`) and then nothing for 30 s. Not proven: why the output fails (the developer shell runs as an unprivileged user and sees no sound cards), and why capture starts an output at all.
