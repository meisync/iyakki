14. **SSH tunnels: see a web page behind a front-facing SSH host** (owner request 2026-10-28, "like VPN"). Design: a tunnel profile (bastion host and port, user, optional jump chain, the target when it is a single page) managed by the agent and shown in Settings -> Network -> SSH tunnels. Three kinds: a LOCAL FORWARD (127.0.0.1:PORT to HOST:PORT through the bastion: one internal page), a DYNAMIC SOCKS proxy (127.0.0.1:PORT: any site the bastion's network can reach) and a jump chain. The program is the OpenSSH client the image already carries for git (`/usr/libexec/iyakki/git-ssh`, BSD) run with FIXED arguments only (`-N`, `-D`/`-L` bound to 127.0.0.1, `ExitOnForwardFailure`, keep-alives, a per-person known_hosts, BatchMode, no ProxyCommand/LocalCommand/Include); keys come from the vault and IYAKKI's in-memory ssh-agent, never from a file path the person types and never on a command line; a host key is shown (fingerprint) and confirmed once, a changed key is a hard refusal (the same rules as `crates/iyakki-agent/src/ssh.rs`). The Browser uses a tunnel for chosen sites only, with the SAME hybrid filter (domain name, URL, CIDR) as the VPN (`crates/iyakki-vpn` FilterSet), so a person can say "open `*.corp.example` through this host, everything else direct". Reconnects with back-off, status in Settings and the top bar, audit lines (names only), nothing public bundled: the person supplies their own host and key. **Several tunnels at once (owner, 2026-10-28):** the page is a list; the person adds as many as they like, and each one can be ENABLED or DISABLED (an enabled one starts with the device and reconnects, a disabled one is kept but never started), edited, and DELETED (asks first; its vault entry and known_hosts line are removed with it). Local ports are allocated per tunnel without clashes (a taken port is reported, never silently reused), each tunnel shows its own state (connected since, last error in words) and the Browser rule list names the tunnel a site goes through. The same list model (add, enable/disable, delete, per-item state) is used for VPN profiles. **Status 2026-10-28: manager, argument allow-list, Settings page, assistant tools and docs/SSH-TUNNELS.md built and tested with a fake client; not yet tried against a real SSH host; Browser per-site routing is the seam `sshtunnel::SiteRouter` (not wired).**
15. **Browser: custom request headers by domain and URL** (owner request 2026-10-28). Settings -> Browser -> Custom headers: a list of rules; each rule has a name, a FILTER (domain name with wildcard, URL prefix, the same matcher as the VPN and the SSH tunnels), one or more headers (name and value), and can be added, edited, ENABLED, DISABLED and DELETED (delete asks first). Use: a token or an `X-` header for an internal site, a test header for a staging page. Rules: header values that are secrets (a token) live in the vault and are marked secret in the list (shown masked); the header is sent only to requests that match the filter, only over https unless the rule says otherwise for a local address, and is DROPPED when a redirect leaves the matching site; names the browser must own are refused (`Host`, `Content-Length`, `Transfer-Encoding`, `Connection`, `Upgrade`, `Proxy-*`, `Sec-*`, `Cookie` and `Authorization` need an explicit "I know" tick), no CR/LF or control characters, at most N rules and a size cap; the page-info line shows "custom headers active here (n)"; audit lines list rule names, never values. Where it runs: the in-house engine adds them in the HTTP client (`crates/iyakki-web`); the full engine (WPE) needs a web process extension that hooks `WebKitWebPage` `send-request` and appends to the request's headers for the matching sub-resources too (a helper-side C extension, compile-checked with the image toolchain, proven on the Mac). **Shared filter:** extract `FilterSet` from `crates/iyakki-vpn` into its own small crate before the second feature uses it, so the VPN, the SSH tunnels and this one share one matcher and one set of tests.
16. **Chat assistant tools for VPN and SSH tunnels, with the person's approval** (owner request 2026-10-28: "expose VPN and SSH tunnel to chat, with user approval, it can add configure for user"). Read-only tools run without a card: `vpn_status`, `vpn_inspect` (the same safe summary as `iyakki vpn inspect`), `ssh_tunnel_list`. Every tool that changes something asks the person on a card that says in plain words exactly what will change (host and port, kind, mode, filters, the role of a key, which sites go through it) and is on the HARD-ASK list: it asks every time, even in Auto mode, and "Allow for this session" does not remember it. Write tools: `vpn_import` (a profile file the person already put in an allowed place; the file is parsed locally, secret blocks go straight into the vault, the model gets only the summary, never the file text, keys or tokens), `vpn_set_mode`, `vpn_set_filters`, `vpn_enable`/`vpn_disable`/`vpn_delete`, `vpn_connect`/`vpn_disconnect`, `ssh_tunnel_add`/`ssh_tunnel_edit`, `ssh_tunnel_enable`/`ssh_tunnel_disable`/`ssh_tunnel_delete`. Secrets: the assistant never asks for a key or password in the chat and never sees one; it calls the vault request flow (the person types or picks the secret in the vault dialog) and refers to the entry by name. ## Rules for every item

- A fix is not done until it ran on the real image: QEMU boot test for every image, and the Mac for anything touching hardware, the browser or the cluster.
- A test that uses a fake runner for a program must have a second check that the program exists on the image.
- Nothing proprietary ships; downloads happen at the person's click.
- Nothing is committed until the owner says so.
