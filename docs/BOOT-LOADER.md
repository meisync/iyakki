# The extra boot loader on the image (test entry)

IYAKKI's own boot loader (`iyakki-boot/`, standalone, MIT OR Apache-2.0) is on the install and lean images as an extra, selectable
entry. GRUB stays the default way in; the loader has not yet booted on any real machine.

## What the image carries

On the boot volume (the FAT partition `IYAKKI-BOOT`, which is the EFI System Partition):

```
/EFI/iyakki-boot/loader.efi   release build of crates/boot-uefi (about 110 KB)
/EFI/iyakki-boot/boot.cfg     the menu (about 8 KB, 26 to 27 entries), generated by boot-loader-stage.sh from ONE table (see "The menu")
/EFI/iyakki-boot/splash.bmp   the IYAKKI emblem, centred on black, 800 x 450, 24-bit BMP (the loader shows it while it starts)
```

GRUB's menu gets "IYAKKI - new boot loader (test)" inside "More options...": `chainloader /EFI/iyakki-boot/loader.efi`. It is shown only on UEFI
and only when `loader.efi` is on the volume, so BIOS starts, the live ISO and builds without the loader look exactly as before.
It needs GRUB's `chain` module, which is in the EFI module list of `configs/iyakki_x86_64_defconfig` (a GRUB rebuild).
Since 2026-11-07 the loader IS the default of every UEFI image build (`IYAKKI_LOADER_DEFAULT` defaults to 1, next section); `IYAKKI_LOADER_DEFAULT=0` keeps GRUB as the default, and a build that never built the loader program keeps GRUB with a message. The plan to make the loader the default and remove GRUB from UEFI images (never from BIOS images until the loader
has a BIOS stage) is `docs/development/GRUB-REPLACEMENT-PLAN.md`.

## The menu (under the logo)

With no key the default starts after the timeout and the screen shows ONLY the logo. On the first key (or a touch, or Esc/Space at start) the logo
moves up and the menu is drawn BELOW it, on the same background: the first level is `IYAKKI` (the default, highlighted), a countdown line
("Starting IYAKKI in N s") and `More options`; Enter on `More options` opens the second level (a `Back` row first, then safe graphics, remote
diagnostics, compatible USB mode, hardware check, the touch screen tests, trouble 1 to 5, install, NVIDIA, browser, previous version of the loader,
recovery (GRUB menu), UEFI firmware setup, and the systems the scanner found when `scan yes`). Keys: Up, Down, Page Up/Down, Home, End, Enter,
Esc (back from the second level); mouse and touch tap a row (rows are at least 44 px at 1080p, the layout is `boot_core::layout::under_logo`
and works from 640 x 480 to 4K); hold keys at start behave as before.

`boot.cfg` is made by `boot-loader-stage.sh` from the `ENTRIES` table in that script (id, level, title, the kernel command line exactly as in
`board/iyakki/grub.cfg`). `crates/iyakki-core/tests/boot_menu.rs` checks that every GRUB entry has a twin in the table (or is listed as GRUB-only
with a reason; none today) and that the table makes a file the loader accepts, so the two menus cannot drift apart. The rows "Previous version of
this boot loader" (`EFI/iyakki-boot/loader.prev.efi`), "Recovery (GRUB menu)" (`EFI/BOOT/grub-recovery.efi`) and "Full start" (lean images:
`/boot/initrd`) appear only when their file exists on the volume (`requires`); "UEFI firmware setup" only when the firmware can do it.

## How it gets there

1. Build the loader once (the config file name is compiled in):
   `cd iyakki-boot && BOOT_CONFIG_PATH=/EFI/iyakki-boot/boot.cfg cargo build --release -p boot-uefi --target x86_64-unknown-uefi`
   (or point `IYAKKI_BOOT_EFI` at such a file). Without a built loader the image builders skip all of this and say so.
2. `dist/buildroot/boot-loader-stage.sh ROOT [INITRD]` writes the three files into `ROOT/EFI/iyakki-boot/`. `board/iyakki/post-image.sh`
   calls it for the install template (`install-root`, RAM disk `/boot/initrd`); `lean-image.sh` calls it again for the lean image
   (RAM disk `/boot/initrd-lean`) and copies the files into the boot volume.
3. `board/iyakki/boot-splash.py` makes the picture from `crates/iyakki-shell/assets/logo.png` (the owner's logo) with the Python standard
   library only.

## The loader as the default: `IYAKKI_LOADER_DEFAULT` (default 1 since 2026-11-07; 0 keeps GRUB)

With `IYAKKI_LOADER_DEFAULT=1` (the default) in the environment of the image build (`board/iyakki/post-image.sh` for the install template, `lean-image.sh`
for the lean image; the update pack is made from such an image and needs no option), `dist/buildroot/loader-default.sh` rearranges the
boot volume after `boot-loader-stage.sh`. With `IYAKKI_LOADER_DEFAULT=0` nothing below happens and the image is laid out as the alpha images were (GRUB default). Owner decision 2026-11-07, after the HP, the Lenovo and the Macs booted through the loader: every pack made from now on carries the loader-default layout, and a pack of such an image moves a GRUB-default disk to loader-default by the rename rule below.

```
shim path (the image is signed: IYAKKI_SB_KEY / IYAKKI_SB_CERT set)        plain path (no shim: unsigned image, or an internal disk)
  EFI/BOOT/BOOTX64.EFI        shim, unchanged                                EFI/BOOT/BOOTX64.EFI        the loader
  EFI/BOOT/grubx64.efi        the loader (SBAT, signed with the image key)   EFI/BOOT/grub-recovery.efi  GRUB (was BOOTX64.EFI)
  EFI/BOOT/grub-recovery.efi  GRUB (was grubx64.efi; signed as before)       EFI/iyakki-boot/loader.efi  the same loader
  EFI/iyakki-boot/loader.efi  the same signed loader (the updater's copy)    EFI/iyakki-boot/{boot.cfg,splash.bmp}
  EFI/iyakki-boot/{boot.cfg,splash.bmp}, EFI/BOOT/mmx64.efi, EFI/IYAKKI/*
```

* Signing: `secureboot.sh loader-image` (SBAT section from `board/iyakki/loader-sbat.csv`, then the image key). With no key configured the
  loader is left UNSIGNED and the script says so: that image starts with Secure Boot off only. (A shim layout without a key gets the same message: shim refuses an unsigned second stage when Secure Boot is on.)
* The loader's `boot.cfg` has the "Recovery (GRUB menu)" row (`kind chain`, `/EFI/BOOT/grub-recovery.efi`, shown only when the file exists), so
  the file names above and the config always agree; the script checks that the row is there.
* GRUB's own "new boot loader (test)" entry is dropped from `boot/grub/grub.cfg` (the block between the `loader-test-entry` markers); on a
  GRUB-default build it stays.
* The live ISO is not changed: it keeps GRUB (it must start on BIOS too). The BIOS part of any disk keeps GRUB as well.
* Update packs: `iyakki dev update-pack` copies every file under `EFI/`, so a loader-default pack replaces `EFI/BOOT/grubx64.efi` (or
  `BOOTX64.EFI`) and adds `grub-recovery.efi`. `iyakki dev update` writes every file of `EFI/BOOT/` and `EFI/iyakki-boot/` beside the old one
  and renames it, and orders the EFI writes so that `grub-recovery.efi` comes first, then the loader's folder, then the files the firmware or
  shim start by name (`grubx64.efi`, `BOOTX64.EFI`) last: at every moment of a power cut the second stage is one whole file (GRUB or the
  loader), and once it is the loader, GRUB's recovery copy is whole beside it (tests in `devmode/tests_update_safety.rs`).
* The installer (`iyakki-usb`) clones the boot volume of the image, so a loader-default image installs with this layout without any change.

### Moving the Mac mini's internal disk from GRUB-default to loader-default (the owner's steps)

1. Build the loader-default image (`IYAKKI_LOADER_DEFAULT=1`, the owner's key configured as for every signed image: the SAME key as the
   installed one, or MokManager must enrol the new certificate once), boot it in QEMU first (rule: boot every new image in QEMU before the Mac).
2. Make the pack with `iyakki dev update-pack IMAGE -o DIR` and send it with `iyakki dev update` as for any update (pairing and approval are
   unchanged). The device keeps the running kernel and RAM disk as "IYAKKI (previous version)" in GRUB first, then writes the EFI files in the
   order above: `grub-recovery.efi` (the old GRUB, whole), `EFI/iyakki-boot/*`, and last `EFI/BOOT/grubx64.efi` (it was GRUB, it is now the
   loader). Restart.
3. On the Mac: the firmware picker (hold Option at power on) lists the same volume as before (`IYAKKI-BOOT`); shim starts, finds `grubx64.efi`
   and, because the same key is enrolled in MOK, accepts the signed loader with its SBAT section. The T2 security level must be the one that
   already starts shim today (Full Security with the Microsoft CA allowed, or Medium); the loader needs no other level. If the Mac boots the
   volume without shim (No Security, volume without shim), the plain path applies: `BOOTX64.EFI` is the loader. MokManager enrolment: nothing
   new for a key that is enrolled; a different key asks for the blue screen once (`EFI/IYAKKI/iyakki-mok.cer`, "Enroll key from disk").
4. Check: the logo appears, any key opens the menu (keys already in the firmware's buffer when the loader starts, such as the Enter that chose the disk in a Mac's startup picker, are discarded first; the log says "input: N key(s) were already in the firmware's buffer", added 2026-11-08 after the MacBook Pro stopped in the menu), and on Apple firmware the hardware listing counts the USB interfaces without asking them (the USB I/O descriptor call never returned on a MacBookPro14,1: logo shown, log ending at "next: USB", 2026-11-08; the log is now written after every section of the listing, so a stop names its section), verified the same day: the MacBookPro14,1 boots with that loader; and on Apple firmware the serial console parameters (`console=ttyS0,115200`) are dropped from the kernel command line, because on the 2016-2017 MacBook Pros ttyS0 is the Bluetooth chip's serial link and a kernel console there kills Bluetooth (2026-11-08), "More options" lists "Recovery (GRUB menu)", the sign-in screen appears and the next start
   shows no failure message (the start is confirmed by IYAKKI).

Rollback, one step at a time: (a) at the loader, "Previous version of this boot loader" if there was an earlier loader; (b) "Recovery (GRUB
menu)" starts the old GRUB with its whole menu, including "IYAKKI (previous version)"; (c) from a running system, `iyakki dev update` with
a pack of a GRUB-default image (a downgrade needs `--force`) puts GRUB back as `grubx64.efi` / `BOOTX64.EFI` by the same rename rule and leaves
the loader files; (d) with nothing running: hold Option at power on and start the stick that installed the system. Nothing here touches the
data partition.

Not tried on any real machine (QEMU only): the Mac's firmware picker, T2 security levels, MokManager with the real Microsoft shim, a PC's firmware.

## Secure Boot and MOK

The loader works in the shim chain (tested in QEMU with the Secure Boot firmware, `iyakki-boot/tools/qemu-secureboot-test.sh`):

* shim (`EFI/BOOT/BOOTX64.EFI`) loads its second stage by the name `grubx64.efi`. On a loader-default image that file is the loader: signed with the
  IYAKKI key and carrying an SBAT section `iyakki.loader,1,...` (`secureboot.sh loader-image IN OUT`: `iyakki-boot/tools/add-sbat.sh` with
  `board/iyakki/loader-sbat.csv`, then `sign-pe`). The key is the same one that signs GRUB, the kernel and the kernel modules. shim 15.3+ refuses a
  second stage without `.sbat`.
* The loader starts the kernel with `LoadImage`/`StartImage` and the initrd through `LoadFile2` (as GRUB, unsigned). shim's security override does
  not cover images the second stage loads, so the loader wraps the firmware's `Security2Arch.FileAuthentication` while it starts something: the
  firmware's answer stands when it is yes, and on no shim's `ShimLock.Verify` decides (MOK list). (`crates/boot-uefi/src/shim.rs`.)
* MOK enrolment is unchanged: MokManager (`mmx64.efi`) enrols `EFI/IYAKKI/iyakki-mok.cer` once.
* Today (GRUB default) `loader.efi` on the image is NOT signed by the image steps: sign it with `secureboot.sh loader-image` before it is chain
  loaded under Secure Boot (the firmware refuses it unsigned and GRUB returns to its menu).

Not tried on real hardware: any of this on the Mac mini or a PC with real shim. QEMU runs of the loader-default layout (plain, shim with
Secure Boot off, shim with Secure Boot on, the Recovery row) are listed in `docs/development/GRUB-REPLACEMENT-PLAN.md` section 2.

## Boot confirmation and rollback

The loader counts a start it chose by itself (`tries`, 9) and refills the count when the running system confirms. IYAKKI confirms after the shell has
started drawing (`iyakki_core::bootconfirm`: UEFI variable `BootConfirm`, vendor GUID of the loader, through efivarfs). After `tries` unconfirmed
starts the loader switches to "previous", after `tries` more it stops and opens its menu with the reason on screen. Choosing by hand never spends a
try. Details and the update path (`loader.prev.efi`, temp name and rename) are in the replacement plan.

## Rows that GRUB's recovery job needs (2026-11-07)

Two first-level rows work without GRUB. The menu is `timeout 0`: it opens only when a key is held, after a start that came back, or when the
loader stops to wait.

**IYAKKI (previous version).** The system update (`crates/iyakki-agent/src/devmode/update.rs`) already keeps the kernel and RAM disk it replaces
on the data partition (`boot-prev/<id>/`, ext4), where GRUB reads them. The loader reads FAT only, so a loader that read that partition would
need an ext4 reader in the boot path (a large new piece, in a program that runs before the kernel and under Secure Boot). Chosen instead: the
update ALSO copies the same two files to the boot volume, `EFI/iyakki-boot/prev/bzImage` and `prev/initrd`, then writes one marker, `set-plain`
or `set-oldroot` (the second when the update also replaced the system image: that row adds `iyakki.root=previous`, exactly like GRUB's entry). The
rows `prev-plain` and `prev-oldroot` in `boot.cfg` `require` their marker, so they exist only when a complete copy exists: the marker is removed
first and written last, files go through a temporary name and a checked rename. It is best effort: with the lean install the pair is about
15 MB; a full RAM disk (about 300 MB) usually does not fit beside the new files on the 512 MB volume, then the update says so in its result
(`loader_copy`) and only the GRUB entry remains. Own code, no new dependency. The row has the same title as GRUB's, shown on the first level
only when a copy exists (otherwise hidden).

**Automatic fall back.** The default row names the two rows in a new `previous` line. When the boot state says the previous version is due
(`tries` unconfirmed starts, `BootConfirm` never arrived) the loader starts that row instead of the default, without opening the menu
(`boot_core::choose::previous_item`). The marker holds `stamp N`, one more with every update; the stamp is stored in the boot state
(`BootState::sync_stamp`), and a new stamp means a new set was installed, so the tries and the choice of the current version start over (without
it a rollback would outlive the next update). With no previous copy nothing changes: 9 starts, then the old behaviour (same files, 9 more, then
the menu waits with the reason on screen). If the previous version fails too, the menu waits as before. Choosing a row by hand never spends a try.

**Install to a disk.** The row starts the same kernel and RAM disk as the normal row with `iyakki.install=1` (the command line is the one GRUB's
entry uses; a test compares them), so it does not depend on GRUB. It is a first-level row only on install media (`requires
/EFI/iyakki-boot/install-media`; update packs and installed disks leave the marker out). It is deliberately NOT offered under More options of an
installed disk: the installer never lists the disk it started from as a target and an installed disk carries no install image, so there is nothing
useful to offer, while a wipe-a-disk row on the machine's only system disk is a risk (the running desktop's own Install page, `iyakki install`,
stays for that case). Revisit when a reinstall-to-another-disk use is asked for.

Tests: boot-core (`choose::tests::fallback::*`, `assess::tests::a_new_stamp_*`, `config::tests::previous_names_*`); the generated rows in
`crates/iyakki-core/tests/boot_menu.rs`; the update side in `devmode::tests_update` (`the_loader_copy_*`); QEMU (`iyakki-boot/tools/qemu-test.sh`,
tests `k` and `l`, stand-in kernel: sequence of starts and the rows present or absent). Not proven: a real kernel started from the copy on the
boot volume by the loader (firmware USB reads of the copy), the Install row starting the real installer through the loader, and any of it on a
real machine.

## The boot log on the volume (`EFI/iyakki-boot/last-boot.log`)

A laptop has no serial port and the splash hides the text console, so the loader keeps every line it would have printed and writes
them to `EFI/iyakki-boot/last-boot.log` on the boot volume (the root `/last-boot.log` when that directory is missing; nothing when the
medium is read-only). It is written four times in a run, each time the whole log so far: after the device summary, when the entries
are known, right before a start (the file's last line then says `log: about to start` and the line above it `start: iyakki kernel=...`:
a kernel that never draws anything is still named), and after a start came back with its error. Added 2026-11-07 for the HP laptop that
stopped where the Macs and the Lenovo did not; `iyakki-boot/tools/qemu-test.sh` (test a) reads the file back from the test disk.

The log starts with a device summary (`hw:` lines, `crates/boot-uefi/src/hwlog.rs`), read only, nothing connected or changed:

* `hw: firmware`: vendor, revision, UEFI version, Secure Boot, setup mode, TPM 2.0 protocol present or not;
* `hw: BIOS`, `hw: machine`, `hw: board`: SMBIOS types 0, 1 and 2 (vendor, product, version, family; no serial numbers);
* `hw: memory`: usable RAM, reserved, MMIO, the highest RAM address;
* `hw: pci`: every PCI function with vendor:device, class and plain words (an Intel RAID-class function is flagged as VMD: the NVMe behind
  it needs the `vmd` driver);
* `hw: usb`: every USB interface with vendor:product, class and the firmware's device path;
* `hw: disk` / `hw: partition`: size, block size, removable, read-only, whether the firmware can read a file system on it, device path;
* `hw: screen`: each graphics output's resolution, mode count, pixel format and frame buffer;
* `hw: input`: counts of keyboards, mice, touch screens (absolute pointer) and serial ports.

To read it, plug the stick into any computer and open the file. To patch a loader on a stick by hand (a loader-default image with shim):
sign it with `secureboot.sh loader-image IN OUT`, keep the old `EFI/BOOT/grubx64.efi` as `EFI/iyakki-boot/loader.prev.efi` (the
"Previous version of this boot loader" row), then copy the signed file over `EFI/BOOT/grubx64.efi` and `EFI/iyakki-boot/loader.efi`.

## What is not carried over

GRUB's Compatible USB mode variable (`iyakki_usbq`, from Settings -> Storage) and the lean-start failure fallback are GRUB features; the loader's
entries do not read them (the explicit "Compatible USB mode" row is carried). The loader reads FAT only: the previous kernel that `iyakki dev update`
keeps on the data partition is also copied to the boot volume for the loader's "IYAKKI (previous version)" row (see above), so GRUB's recovery entry
is no longer the only way to it.
