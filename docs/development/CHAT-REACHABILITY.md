# Chat reachability: every Settings page has an assistant tool

Owner rule (2026-11-06): every feature is reachable by chat. A change is an assistant tool that asks the person every time; a read is free. A tool calls the same service code the page calls (one shared path), never exposes a secret, and writes an audit line.

This file is read by a test (`chat_reachability_gate` in `crates/iyakki-apps/src/apps/chat_reachability_tests.rs`). Rules the test enforces:

* every row names a Settings `Tab` in the first column; every `Tab` has a row;
* a row with tools names tools that exist in the source; a row without tools (`MISSING`) must be listed in `chat-reachability-exempt.txt` with a reason;
* an exempt page that gets a tool must leave the exemption list (the list only shrinks).

Risk classes: `free` = read only, no card; `ask` = changes something, a card every time, no session grant (`grant_blocker`), never "always allow"; `hard` = destructive or secret-adjacent, the card is the full plan.

How a tool is built: `crates/iyakki-agent/src/settingstools.rs` is the frame (`Entry`, `SettingsTools`); a page contributes `Entry` values (`settingstools_<page>.rs`, or `apps/chat_settings.rs` when the code lives in the shell). Each has unit tests in the same module and is classified in the system prompt rule (`PROMPT_RULE`) that the chat adds for the person's role.

## Not on a page

Sign-out is a power-menu action (`shell_signout.rs`, not edited in this slice): a `sign_out` tool needs a request file that the shell takes, as `lock_screen` does. It is listed in `chat-reachability-exempt.txt` as a todo for the owner of that file.

## The PDF output switch

`native_pdf_output` (a provider or an external agent writes PDF files itself, so `pdf_create` is not offered to it) is a key on the Models page (`P`) and the Agents page (`p`), and has the assistant tools `pdf_output_status` (free) and `pdf_output_set` (ask every time, with a card that names the old and the new state; administrators only). Covered; they are listed with the `Models` and `Agents` rows above.

## Tiles that write files (not Settings pages)

* PDF (docs/PDF.md): `pdf_info`, `pdf_text` (free), `page_save_pdf`, `pdf_form_fill` (fills form fields into a new file) and `pdf_create` (ask; `pdf_create` is offered to every model that does not write PDFs itself; a provider or external agent with `native_pdf_output` set in its settings is not offered it).
* LEARN: `study_export_pdf` (ask) makes a PDF of a plan, a quiz (answer key page only with `answer_key`) or a day's lesson, through the same function as the tile's Export PDF buttons. Covered.
* TALES: the Save PDF button, the `d` key and a message like "make it a PDF" in its conversation write `Stories/<title>/story.pdf` with the same writer; the general `pdf_create` can also make a PDF of a story from its `story.md`. A web link to a picture (the writer's reply linked to one, or a message like "use https://... for picture 2") is asked about in the tile and fetched only after a yes (F-TALES-18). Covered by the conversation request; there is no separate assistant tool for the TALES tile.

## Embedded assistant (SDK apps)

Not a Settings page and it adds no setting, so it has no tool of its own: the assistant an SDK app embeds (`iyakki_ui_sdk::chatview::ChatView`, facet `iyakki_core_api::assistant`) is already reachable by chat, because it is the chat's own run loop with the app's tools. What switches it is what switches the agent: the account's `agent` policy (Users page, `users` tools); an account without it gets the sentence "The agent is not enabled for your account." in the embedded view. Every tool an app offers that changes something asks the person on a card each time (`ToolApproval::Ask`), is never covered by a session grant (`AppTools::grant_blocker`), and writes `assistant.tool` audit lines (names only, never the message, arguments or context; read them with `session_log` and the audit tools). A future setting for the embedded assistant (a model per app, a switch per app) needs a chat tool in the same change.

|---|---|---|
| Embedded assistant (per app) | none of its own; app tools are declared by each app and reach the model as `app_<app>_<tool>` | free for a read-only app tool; ask (card every time, no session grant) for an app tool that changes something |

## Embedded camera views (SDK apps)

Not a Settings page: there is no Cameras tab, and the switch is one per person, so it has tools and no page of its own (the same as the embedded browser's switch). `embedded_cameras_status` (free) says whether apps may show the person's cameras in their own windows and how many views are open; `embedded_cameras_set` (asks a card every time) switches it, and off closes every open view at once so nothing more is pulled from a camera. What a person may watch is the camera's own list of people (`cameras_access`, F-CAM-17), what a view may show is the person's card at the view (Allow and Deny), and a snapshot or a camera move asks again on a card of the view; none of those is a setting, so none has a chat tool beyond the camera tools that exist. The audit names are `cameras.open`, `cameras.consent`, `cameras.snapshot`, `cameras.switch`, `cameras.close` (names only; read them with the audit tools). A Settings row for the switch is not built; the tools are the way to change it (F-SDK-165).
## Embedded sound player (SDK apps)

The player an SDK app embeds (`iyakki_ui_sdk::audioview::AudioView`, facet `iyakki_core_api::media`) has one switch the person owns: whether apps may play sound in their own windows. Its chat tools are `embedded_media_status` (free: on or off, and how many players are open) and `embedded_media_set` (ask every time; off stops every open player at once). They are listed under the Sound page of Settings. There is no Settings control for the switch yet: the tools are the way (row F-SDK-148). What a player does inside an app (play, pause, seek, volume, speed) is the app's own screen, like any other control of an app; the person's master volume and the sound doctor apply to it because the sound goes through the core's mixer. A remote source (an internet address, a radio station) asks the person on a card first. Audit lines `media.open`, `media.decide`, `media.switch` and `media.close` carry the app and the kind of source, never a file name or an address.
