# UI RPC design: the shell's services over the core socket (F-SPLIT-03, alpha.7)

Goal (owner): the layered build's `ui` layer holds a UI program of a few MB. Today `usr/bin/iyakki` (127 MB, agent inside) is one program in the core layer, because the
shell needs a `ServicesHandle` (200 methods) and the facets it returns. `iyakki-ui --socket` must run the shell with a handle whose calls cross the socket, so the UI
program does not link `iyakki-agent`. A Rust dylib is not possible (musl static images), so the crossing is a protocol. Numbers: [UI-RPC-CENSUS.md](UI-RPC-CENSUS.md)
(generated by `dist/split/rpc_census.py`).

## 1. Finding (the stop rule)

The census parses 152 traits and 1,503 methods of `iyakki-agent-api`:

| class | methods | pattern |
|---|---:|---|
| S plain data in and out | 1,114 (74%) | one call |
| IO `&mut T` argument | 23 | send, change, send back |
| H returns `Arc/Box<dyn Trait>` | 116 | remote object id, release on drop |
| R borrowed accessor `&T` | 88 | root object or snapshot |
| E closure or callback argument | 81 | event poll, or the core's own default |
| X UI-owned I/O object passed in (`&dyn Fetch`, `Runner`, `Streamer`, `Arc<dyn Tools>`) | 52 | the argument leaves the signature, the core owns that I/O |
| A `dyn Any`, `as_any` | 29 | never on the wire |

E + X + A = 162 methods (10.8%). The census does not see what is not a trait: the shell and the apps also hold **concrete stateful stores** (`UserStore`, `AuditLog`, and the
14 member types behind `ServicesHandle::settings()`, `inbox()`, `calendar()`, `study()`, `secrets()`, `kb()`, `devwatch()`, `browser()`, `screen()`, `camera()`, `devtools()`,
`ext_status()`, `secret_requests()`, `usage()`: 236 public methods in their `impl` blocks), plus `HostApi`, `Os`, `Core`, `Fetch`, `ChatBackend` which are already contract
or I/O objects. Counting those 236 as unexpressible: (162 + 236) / (1,503 + 236) = 22.9%, below the 30% line, so this is **not** a stop. But the following three things are
real work, not generator work, and they set the order:

1. **The chat tool chain is built in the UI.** About 35 methods (`wrap_*_tools`, `user_tools`, `chat_run_start`, `autopilot_start`, `metered_chat`, `voice_assistant_spawn`)
   take an `Arc<dyn Tools>` or `ChatBackend` and return one. They cannot cross a socket and should not: a chat run, its tools and its approvals belong to the core. Replace
   them by one core-side object `ChatRuns` (start a run with a prompt, poll its events, answer an approval); the UI sends a prompt and draws events. Recommendation: do this
   first, it removes the largest class X/H/E group at once.
2. **The concrete member stores** need a trait each (`InboxApi`, `CalendarApi`, ...) with the same methods, the real one in the agent, the fake in the fake agent, and the UI
   moved from `&Inbox` to `Arc<dyn InboxApi>`. This is the same move that was done for `SessionApi`, `SkillApi`, `RunApi` in alpha.6 (`facets_stores.rs`); 14 types, 236
   methods, mostly S. `UserStore` and `AuditLog` (files the shell reads and appends) become `AccountsApi` and `AuditApi` of the core.
3. **Serde.** Of the 1,114 S methods, 328 name a type with no `Serialize + Deserialize` (196 types, top: `Job`, `Actor`, `Launch`, `VaultError`, `Review`, `Skill`, `Scope`).
   Adding the derives is mechanical but touches `iyakki-shared` in many files; do it type by type as each trait enters `dist/split/rpc-traits.txt`, never in one sweep.

## 2. Wire

The transport is unchanged: one JSON request and one answer per line over the contract socket (`iyakki-ui-client`), bulk by memory file (`bulk.get`).

```text
-> {"id":7,"call":"rpc.call","args":{"obj":0,"iface":"MediaFacet","method":"player","args":[]}}
<- {"id":7,"ok":3}                                            the handle: object id 3
-> {"id":8,"call":"rpc.call","args":{"obj":3,"iface":"MediaPlay","method":"play","args":["ann","song","file:///a.mp3"]}}
<- {"id":8,"ok":{"Ok":null}}                                  a `Result<(), String>` as serde writes it
-> {"id":9,"call":"rpc.release","args":{"obj":3}}             the UI dropped its end
```

`args` is the array of the parameters in order; borrowed parameters (`&str`, `&[T]`, `&T`, `Option<&str>`) travel as their owned form. The reference server decides who the
caller is (`Served::ctx`), never the request. Object 0 is a root: the core registers one object per trait it serves (`Host::with_root`). Ids are per connection; an id from
another connection is "no such object"; a connection that ends frees all its objects; a connection may hold 4,096. The call limit and rate limit of the transport apply.
`iyakki-ui-client` knows only the `RpcServe` trait, so it stays free of the agent; `iyakki-ui-rpc` implements it.

## 3. The generator

`dist/split/gen_rpc.py` reads the traits (the same parser as the census) and `dist/split/rpc-traits.txt` (the traits to serve) and writes
`crates/iyakki-ui-rpc/src/gen_remote.rs` (`Remote<Trait>`: the trait implemented over the connection, plus `RemoteAny` and `remote_any`) and `gen_serve.rs` (`Obj`, one
variant per trait, and a dispatcher per trait). No proc-macro, no new third-party crate (serde and serde_json are already used). Rules per method:

* S: client sends `json!([args])`, server decodes a tuple of owned types, calls the trait method with borrowed forms, encodes the result.
* H: the server stores the handle in the connection's table and answers its id; the client wraps it in `Remote<Sub>` whose `Drop` sends `rpc.release`. A handle whose
  trait is not generated makes the whole trait ineligible. A lost core gives a handle with an id that never exists, so each call on it answers as a lost call.
* Class E/X/A/R with a default body in the trait: left out of the proxy, the trait's own default answers (the existing fakes already return "unavailable").
* Class E/X/A/R without a default and with an owned answer: the proxy answers "not served over the UI socket" through `Lost`.
* A borrowed answer without default (`&T`), a receiver that is not `&self`, generic methods, a trait that is not `Send + Sync`: the trait is not generated and is listed by
  `gen_rpc.py --list` with the reason.
* `Lost` gives each return type its quiet value (`Err(reason)`, `None`, empty list, 0, false). A lost core never panics the UI.

Traits enter `rpc-traits.txt` when their types have serde; the file is the work list and `gen_rpc.py --all-s --list` says how far it could go (108 traits, 680 methods
if every type had serde).

## 4. Patterns for what is not plain data

* **Handles** (`H`): above. `ServicesHandle` has about 50 handle accessors (`b0`, `b3`, `b4`, `b5`, `sessions`, `jobs`, `k3sdev`, ...). They become `Remote*` objects on the
  one shared connection.
* **Closures** (`E`): the contract already uses cursors, not push (`settings.watch(resume, limit)`). A callback argument becomes a subscription: `rpc.call` creates an event
  object, the UI runs one background thread on its own second connection that polls `rpc.events {sub, resume, limit}` and calls the UI closure locally. Audit callbacks
  (`audit: Arc<dyn Fn(&str,&str)>`, about 45 of the 81) are simply dropped from the signature: the core audits its own actions.
* **Streams and blocks**: pull, not push: `read(offset, len)` calls for byte streams, `bulk.get` (memory file) for frames, audio and camera blocks (benchmark: 32 MB in 26 ms).
* **Caller-supplied I/O** (`X`: `Fetch`, `Runner`, `Streamer`, `Kube`): removed from the signature; the core uses its own network and command runner, which is also the
  right place for the approval and the audit of that I/O.
* **Borrowed accessors** (`R`, `&T`): a root object per accessor (returned once, kept for the life of the connection) or, for plain data, a read-model snapshot.
* **`&mut T`** (`IO`): `[value]` out, `{ret, value}` back; only 23 methods, the Session saves.
* **`dyn Any`** (`A`, `as_any`, the composition root): never on the wire; the UI program has no composition root over the real agent.

## 5. Latency

Measured: round trip p50 17 us, p99 24 us (UI-BOUNDARY.md section 14). A frame at 60 Hz has 16 ms, so about 900 calls fit, but one connection serves one call at a time under a
mutex, so a pane that calls 20 getters per frame (several do, for example `HostTtsApi::ensure` is documented "cheap to call every frame") would serialize with every other
pane. Rules: (1) no call per frame: the shell reads **read-model snapshots** the core publishes with a revision number (one cheap `rpc.rev` per frame or per event poll,
the data only when the number changes); (2) a `rpc.batch` call (array of calls, array of answers) for pages that need many values at once; (3) caches on the `Remote*` side
for getters the census marks S with no arguments and a name used per frame (measure with a counting wrapper in the first screen test before caching anything).

## 6. Build order

Done in the first piece: census and generator, `iyakki-ui-rpc` (client objects, dispatcher, object table with release), the transport calls `rpc.call` and `rpc.release`
(`Served::rpc`), 27 traits (104 methods) plus `MediaFacet` and `MediaPlay`, loopback tests with a handle, a lost core and a foreign connection, a `cargo tree` test that
the program has no agent, `iyakki-ui-bin` depends on the crate (`remote_services`).

Done in the second piece (impl-rpc2, 2026-11-18):

1. `ChatRuns` (`iyakki-agent-api::chatruns`): `RunRequest` (data), `start`, `poll`, `is_done`, `decide`, `cancel`, `pause`, `forget`; `ChatRunTable` keeps the runs by
   user over a `RunStarter` the core is given. The remote end is generated. **Still to do:** a real `RunStarter` in the core that builds the tool chain
   (`apps/tool_chain.rs`, the `wrap_*_tools` calls in `apps/chat.rs`, `autopilot_start`, `metered_chat`, `voice_assistant_spawn`); today those still run in the UI
   because they read `AppCx` (the open project, the dashboard, the flows, the task list). Moving them means giving the core those states by name.
2. Member stores: `dist/split/gen_store_api.py` writes `member_stores.rs` (15 traits, 150 `&self` methods, `impl` for each type, a `*Via` adapter over the
   `ServicesHandle` accessor for the 12 that have one). Left inherent: `&mut self`, generic, closure and borrowed-answer methods. Not served: `SettingsApi`,
   `KnowledgeBaseApi`, `AccountsApi` (borrowed answers or a mutex around the store) and `CameraHubApi` (returns a handle of an unserved trait). The shell has not moved
   from `&Inbox` to `Arc<dyn InboxApi>`; that is the work that unblocks `RemoteServicesHandle: ServicesHandle`.
3. Serde derives (`dist/split/add_serde.py`, by `module::Type`): 30 types so far.
4. Trace: `RecordingServices` (generated by `gen_recording.py`) under the shell; `shell::trace_tests` pins the 9 `ServicesHandle` methods of the launcher and the
   Settings overview (b4, camera, dir, mcp, radio, screen, settings, sound_settings, store_facets). Calls on the returned handles are not traced.
5. `iyakki_compose::rpc::RpcRoots`: 20 roots over the real services plus `AuditApi` and `ChatRuns` when given; `uiserve::served` passes `rpc: Some` when the socket's
   config has `rpc: true` (`ui_socket_set rpc`, off by default); `iyakki-core` main wires the factory.
6. `RemoteServicesHandle`: accessors over the connection, `is_real` true only while the core answers.
7. `RemoteServicesHandle: ServicesHandle` (alpha.7 final wave, `dist/split/gen_services.py`, D-SPLIT-03-HANDLE): the core serves one more root, `ServicesHandle`
   (`ServicesRoot`: the real services and the core's own audit callback). The client implementation is generated: plain methods go as `rpc.call` with the data
   arguments only; the accessors of generated traits are roots (the stores) or handles of the root (`contract_local`, `rag_kit`); the audit callbacks are left out of the
   wire; the borrowed answers (`dir`, the two prompt rules, `mcp`, `secrets`) are kept in the handle; the closures that change a value (`update_sound_with`,
   `update_system_sounds_with`) read the whole value, change the copy and write it back (`set_sound_settings`, `set_system_sounds`); everything else answers the quiet value
   of its type, and an accessor of a trait that is not generated yet answers an `Unserved` object (`gen_unserved.py`) or the default of its trait (`NoStoreFacets`).
   `services-unserved.txt` lists the plain methods whose types cannot cross yet (no serde).

Next, in this order:

1. The real `RunStarter` (point 1 above), then `chat.rs` sends a `RunRequest` and draws events; the ~35 chain methods leave the UI.
2. The shell moves from the concrete stores to the member traits (the ratchets pin the counts); `SettingsApi` and `KnowledgeBaseApi` need the lock inside the adapter.
3. `RemoteServicesHandle: ServicesHandle`: done (point 7 above); what remains of it is to generate the traits of the 48 accessors one by one so they leave `Unserved`.
4. `iyakki-ui --socket` builds `ShellEnv` from it and runs the launcher and Settings; a QEMU run with `iyakki.ui=process`; the ui layer is built without the agent and
   its size measured.

F-SPLIT-03 reaches 100 only when step 4 runs the whole shell; until then Impl counts the generator, the transport, the objects, the roots and the proofs above (66).
