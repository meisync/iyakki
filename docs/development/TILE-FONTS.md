# Tile fonts (F-WASM-13): design, for the owner's decision

Status 2026-11-15: option A is built (row F-WASM-13), as the recommended default; the choice between A, B and C stays the owner's to overturn. Built: `dist/tilefont/gen.py` makes the table from the shell's DejaVu Sans, Sans Mono and Sans Bold (faces 0, 1, 2 of the ABI) at the sizes 8, 10, 12, 16, 22 and 32, for ASCII and Latin-1, as one-bit cell bitmaps of the ABI's advance (`6 * size / 7`) by the size; it writes `crates/iyakki-tile-host/src/tilefont.bin` (123 KB, read by `font.rs` and the reference renderer) and the same bytes as base64 into `ui/tilerender.js` (the browser renderer, about 165 KB more), and `gen.py --check` (run by a test) fails when either differs. A size that is not listed uses the nearest cell, scaled by whole-number sums that both renderers share (a tie goes to the larger). Glyph shapes are widened by a factor of at most 1.2 to use the ABI's wide cell and are centred in it; a character outside ASCII and Latin-1 draws as `?` (as before). It stays one-bit (no anti-aliasing), so small text is crisp and a little jagged; real proportional text is still option B (ABI version 2).

## What there is

The reference renderer (`iyakki-tile-host::render`) and the browser renderer (`ui/tilerender.js`) draw text with one 5x7 bitmap font
(upper case; lower case draws as upper case; anything else as `?`) at the ABI's fixed advance of `6 * size / 7` pixels per character
(`iyakki_tile_abi::measure_text`). The three faces (sans, mono, bold) look alike. A tile measures text with the host's `measure_text`
import, so what the tile lays out is what is drawn, on the device and in the browser. The shell's own apps use real fonts (DejaVu Sans,
Bold, Mono) and are not affected.

## The choice

The advance is part of the ABI (version 1). That is what decides everything:

* **Option A: real glyph shapes, same advance (no ABI change).** Take the glyph shapes from DejaVu Sans Mono (a fixed-advance font, so a
  character fits its cell at `6 * size / 7` without squeezing; the cell is narrower than the font's own 0.6 em advance, so the shapes
  are scaled by a factor of about 0.99 at every size). Store them as a table of outlines or, simpler and exact in both renderers, as
  coverage bitmaps at a few pixel sizes (7, 9, 11, 13, 16, 20, 24, 32) for printable ASCII and Latin-1 (about 190 characters). Larger
  or other sizes use the nearest listed size, scaled by whole numbers (the same rule the renderers already use for the 5x7 font).
  Cost: about 190 glyphs x 8 sizes x (size squared / 8 bytes) is roughly 60 KB of table in the Rust crate and the same in
  `tilerender.js` (base64 inside the file or a separate `tilefont.js`), generated by one script from the font so the two cannot differ.
  Sans and Bold would look like mono letters at a mono advance: legible, not pretty.
* **Option B: ABI version 2 with measured text.** The host measures with the real font's advances (proportional) and the tile gets the
  true widths. Then DejaVu Sans, Bold and Mono can each be used properly. Cost: a new ABI version, both renderers and every tile's layout
  code change, and the width table of each face (about 600 numbers) is part of the ABI; old tiles keep working only if the host keeps
  v1 measuring for them.
* **Option C: leave the 5x7 font.** It is honest and works everywhere; tiles that need text people read use the shell's own apps or the
  full web UI instead.

## Licence and size

DejaVu fonts are under the Bitstream Vera licence with DejaVu changes (permissive; already listed in `LICENSING.md` for the shell).
A table made from the font is a derived work and needs the licence text with it (a comment block at the top of the generated file and
an entry in `LICENSING.md`). No new font is added: the same files the shell bundles.

## Verification when built

The golden test already compares the two renderers pixel for pixel (tolerance 0) in real Chrome (`dist/browsertest/run_pages.py
--only tiles`); a glyph sheet of every table character at every table size is added to it, and the table is generated by one script that
both files embed, with a test that regenerating gives the same bytes.

## Recommendation

Option A first: it changes nothing a tile can observe except that text looks like text, it keeps ABI v1, and the golden test already
guards the two renderers. Option B only when a tile needs proportional text. The owner decides whether option B is wanted later.
