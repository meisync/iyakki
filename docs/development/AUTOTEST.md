# Test automation: `./run.sh autotest`

**For:** people who write scenarios, run the nightly, or turn evidence into the Test column. **Plan:** the 2026-11-21 test-automation plan; owner order: Test rises on machine-made evidence, not on more hand-written unit tests.
Code: `dist/autotest/` (standard library Python; Pillow and tesseract only where `dist/devtest` already uses them). Evidence is written OUTSIDE the repository, under `~/iyakki-work/autotest/<date-time>/`.

## Levels of evidence (never merged)

Every kind of evidence has its own level, its own folder and its own rule. A level never stands in for another.

| Level | Where it lives | Made by | What it proves |
|---|---|---|---|
| `unit` | cited in the row's Tests column | `cargo test`, python unit tests | logic on fakes |
| `qemu` | `OUT/<ROW>/qemu/` | the runner on the real image in QEMU | boot, programs, screens of the image; NOT hardware |
| `browser` | `OUT/<ROW>/browser/` | the Chrome harness | the web client and renderer |
| `machine-<name>` | `OUT/<ROW>/machine-<name>/` (one level per paired machine: `machine-mac-mini-2018`, `machine-lenovo`, `machine-hp`) | the runner on that machine | that machine only |
| `human` | `OUT/human/<ROW>.<clause>.<machine>.json` | a person, in the Doctor tab or the offline page | what only a person can judge (ears, hands, cables) |

`result.json` carries `level`; the migrator's rules are per level: a QEMU result is never a machine result, a unit test is never QEMU. FEATURES.md keeps its nine columns; the Test number is derived from the levels by the rules below, and `docs/TEST-EVIDENCE.md` (with `docs/TEST-EVIDENCE.json` beside it, read-only, generated by `python3 dist/autotest/evidence_report.py`) lists per row which levels have evidence and when.

## Running

```
./run.sh autotest --list                                   # scenarios, rows, targets, format problems
./run.sh autotest --dry-run [--rows F-A-1,F-B-2]           # the plan, nothing booted
./run.sh autotest --profile qemu --image BUILD_DIR [--rows ...] [--update-golden] [--checklist]
./run.sh autotest --profile browser [--rows ...]
./run.sh autotest --profile machine NAME [--rows ...]      # a paired machine, one at a time
./run.sh autotest --checklist --results OUT                # the offline checklist pages from a results folder
```

One run at a time per host (lock `~/iyakki-work/.autotest.lock`), never while the release gate holds its lock, refuses above 85 percent disk. The runner never builds, never signs in, types no password; the QEMU guest is a scratch account that is deleted at the end. A machine at its sign-in screen or in use gives BLOCKED for every scenario, never a retry.

## Scenario format

A scenario is `dist/autotest/scenarios/<ROW>.scn`: the `dist/devtest` text format (verbs `key`, `click`, `wait`, `shot`, `expect-text`, `expect-page`, `skip-unless-button`, `restore-click`, ... and its safety guard) plus headers and verbs.
Headers (before the first step): `row: F-A-1, F-A-2`, `targets: qemu browser real hw:macmini2018`, `profile: ram` (QEMU boot profile), `clause: TEXT` (repeat; covered when the scenario passes), `not-covered: TEXT` (repeat; a non-empty list stops every raise), `needs-hw: TEXT`, `human: CLAUSE-ID | what the person must do`, `feature-sha: HEX` (hash of the Feature cell the clauses were written for; `python3 -c "import results; print(results.feature_sha(TEXT))"` in `dist/autotest`), `session-check: NAME` (adapter: runs a check of `dist/qemu/session_checks_defs.py`), `suite: SCRIPT ARGS` (browser target: a `dist/browsertest` script).
New verbs: `expect-golden STEP [mask=x,y,w,h] [budget=PCT]`, `expect-audit REGEX`, `expect-serial REGEX`, `expect-sh CMD ==> REGEX`, `expect-config KEY VALUE`, `expect-http URL STATUS [REGEX]` (loopback only), `covers N` (documentation).
Golden screens: `dist/autotest/golden/<ROW>/<step>.png`; the masked tolerance diff ignores mask boxes and passes under the budget (default 0.5 percent of pixels, 24 per channel); a missing golden is `NEW-GOLDEN` (a candidate, never a pass); `--update-golden` writes it and a person reviews it before it is committed. Text expectations (`expect-text`, OCR) carry the proof; the pixel diff is a regression alarm.

## Result record

`OUT/<ROW>/<level>/result.json`: `row, level, scenario, scenario_file, commit, image, image_commit_source, run_id, target, device, status (PASS, FAIL, SKIP, BLOCKED, NOT-APPLICABLE, NEEDS-HUMAN, NEW-GOLDEN), rung_claim, evidence (paths relative to that folder), covered, not_covered, clauses_attested, feature_sha, screen_evidence, needs_human, ran_at, flaky, reason` (a machine result also `device_ok`). `OUT/run.json` and `OUT/results.json` index a run.

## The evidence rules (`python3 dist/features/migrate-impl-test.py --from-autotest DIR [--apply] [--image-commit SHA]`)

Dry run by default. Test is raised only upward, only by these rules, and nothing is lowered.
* **70** (Test below 70): the two latest `qemu` or `browser` results, from two different runs, both PASS, both on the image commit (known: from `--image-commit` or the gate's RESULT.txt, never guessed), clause list attested (`feature-sha` equals the hash of the Feature cell now), `covered` non-empty and `not_covered` empty, evidence files present and non-empty, the scenario file in the repository, no flaky flag (the same image commit never shows PASS and FAIL), not older than 14 days, Impl 100. The Tests cell gets `script:dist/autotest/scenarios/<ROW>.scn`.
* **Nothing** on SKIP, BLOCKED, NOT-APPLICABLE, NEEDS-HUMAN, NEW-GOLDEN, FAIL, a stale or unattested result, or a non-empty not-covered list.
* **100 from QEMU: never** by default. The switch `--qemu-counts-as-real` (OFF; owner decision pending: does QEMU count as real for software-only rows) lets a screen-evidenced, two-run PASS set 100 for a row with Manual `none`. A FEATURES row at 100/100 is set `done` (feature_matrix requires it).
* **100 from a machine**: a PASS at the `machine-<name>` level with `device_ok` (the hardware matches), all clauses covered, and for every `needs_human` clause a human file with verdict `pass` for that machine and image commit; Manual becomes `passed DATE MACHINE`.

## Human checklist contract (shared with the Doctor tab, branch alpha.7/H1)

Code and validators: `dist/autotest/humanschema.py` (tests `dist/autotest/tests/test_humanschema.py`). Both shapes are JSON with `"schema": 1`. The in-OS Doctor tab and the offline HTML page read the first and write the second, the same.

**Checklist file** `dist/autotest/checklists/<ROW>.json` (example: `F-SDK-216.json`):
```
{"schema":1, "row":"F-X-1", "feature_sha":"16 hex of the Feature text", "title":"short name for the left nav",
 "clauses":[{"id":"ears-1", "text":"what this clause of the Feature asks", "machines":["any"|"qemu"|"mac-mini-2014"|"mac-mini-2018"|"macbook-pro"|"lenovo"|"hp"|"t7-ssd"|"other"],
   "steps":[{"do":"press Play on the tone", "expect":"two notes, left then right", "runner_did":"optional: what the runner already did", "screenshot":"optional relative path"}]}]}
```
Rules: ids are plain (`A-Za-z0-9_-`, up to 48), unique per file; steps and expectations are plain text (up to 2000 characters); paths are relative, no `..`; `machines` names the kinds that can answer the clause (a clause for `any` may be answered on any machine, others only on the named kinds).

**Human evidence file** `human/<ROW>.<clause>.<machine>.json` (the machine id is a plain name such as `lenovo` or `mac-mini-2018`):
```
{"schema":1, "row":"F-X-1", "clause":"ears-1", "machine":"lenovo", "image_commit":"abc1234", "by":"owner", "verdict":"pass"|"fail"|"cannot-test",
 "date":"2026-11-22" or "2026-11-22T10:15:00", "note":"optional", "photo":"optional relative path"}
```
No field outside this list is allowed; nothing secret is collected. Only `pass` for the same machine and image commit counts (rule 100 above); `fail` opens a KNOWN-ISSUES draft; `cannot-test` counts for nothing and stays visible.

The offline form is `./run.sh autotest --checklist`: one HTML page per machine kind (`OUT/checklist/<machine>.html`), the runner's screenshots embedded, Pass, Fail and Cannot-test buttons. Opened as a file it saves each answer as a download with the right file name; served by `python3 dist/autotest/checklist.py --serve OUT` (loopback only) it writes into `OUT/human/` directly. It works offline and needs no cloud.

## Nightly and triage

`python3 dist/autotest/nightly.py plan|run STEP|triage|install` (documented only; nothing here enables a cron or a timer). One lock for all steps. 01:00 gate and image on the AMD host, 02:30 autotest QEMU and browser, 04:00 paired machines one at a time (a machine whose sign-in screen shows is skipped as BLOCKED), 06:30 triage. Triage: two FAILs in a row draft a KNOWN-ISSUES entry file (never an invented KI number), a PASS and a FAIL on one commit goes to the FLAKY-TESTS suggestions, stale evidence is flagged and never lowers Test. A scenario named in `dist/autotest/quarantine.txt` counts as BLOCKED, never PASS; the list may only shrink.
