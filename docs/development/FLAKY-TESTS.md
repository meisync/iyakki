# Flaky tests: the cure for the class (owner order 2026-11-18)

**For:** anyone who writes or fixes a test.
**You will get:** the rules, the `iyakki-testkit` helpers that make them easy, and how to find the next flake before the gate does.

Every flake the gate showed was a race in the TEST. They share a few causes, and each has one cure in `crates/iyakki-testkit` (a dev-dependency, never shipped):

| Cause | Do not | Do |
|---|---|---|
| Two tests touch one process-wide thing (input state, environment, current folder, the cluster, the audio mixer, a fixed port, a clock override) | hope they never overlap | `let _g = iyakki_testkit::lock(iyakki_testkit::names::INPUT);` around the critical section only. For a `static` of the code under test (it lives inside ONE test process, so other test binaries and parallel cargo runs have their own copy) use `iyakki_testkit::process_lock(name)`: an in-process lock, 15 minutes patience, never makes another process wait. Better still: let the test not touch the static at all (the Keyboard page tests apply to the input layer only when they ask for `live_input()`). Works across threads, test binaries and parallel cargo runs (`flock` under `/tmp/iyakki-testkit-<uid>/`); times out after 120 s and names the holder. `EnvGuard::set(&[("K", Some("v"))])` sets variables under the env lock and restores them. |
| A port number is chosen, freed, then used | `bind(":0")`, drop, reuse; a literal port | `let p = iyakki_testkit::port();` holds the number until `p.release()` / `p.into_listener()`. For "nothing listens": `closed_port()`. |
| Wait for a background effect | `sleep(50ms)`; `for _ in 0..600`; "after 3 beats" | `wait_until(BUDGET, \|\| cond)` (30 s wall clock, polls every few ms, names the last state), `wait_for_state`, `wait_for_file`, `wait_for_line`. |
| A stub child must "run for a while" | `sleep 2` stubs | `GatedChild::start()` lives until `release()`; `ChildGuard` kills and reaps on drop; `wait_gate_snippet(gate)` for stub scripts. |
| A test asserts speed | `elapsed < 50ms` | assert the behaviour; where speed is the point inject `ManualClock` and `advance` it, or, for "this call is cheap on the UI thread", compare `iyakki_testkit::thread_cpu_time()` before and after (a loaded machine stretches wall time, not the thread's CPU time). |

Never weaken an assertion that checks behaviour, never add a test to `dist/release/known-flaky.txt` (the mechanism stays, the list is empty), never use `#[ignore]` to hide a flake.

## Finding them
* `python3 dist/scripts/flaky-patterns.py` scans all test code for the risky patterns and writes `docs/development/FLAKY-AUDIT.md` (counts per crate).
* The ratchet test `flaky_pattern_ratchet` (iyakki-core tests) fails when a crate has more risky hits than `docs/development/flaky-ratchet.txt` allows; the numbers only shrink.
* `dist/scripts/flake-hunt.sh` runs a test filter N times in parallel under CPU load and lists the tests that failed at least once (see its header).

## The flake hunter
`dist/scripts/flake-hunt.sh -p CRATE [-n RUNS] [-j PARALLEL] [-T TEST_THREADS] [-l BURNERS] [-f FILTER]` builds the crate's unit-test binary, then runs it RUNS times (PARALLEL at a time, TEST_THREADS threads each, far above the core count) next to BURNERS busy-loop processes, and lists every test that failed at least once with the number of runs it failed in. Examples (on a build host, in the worktree copy, `cargo` on the PATH):

    ulimit -n 10240
    bash dist/scripts/flake-hunt.sh -p iyakki-shared -n 10 -j 4 -l 8
    bash dist/scripts/flake-hunt.sh -p iyakki-apps -n 3 -j 3 -T 32 -l 6 -f jobs_screens

* A test that fails in EVERY run on a Mac is usually a Linux-only test (see LINUX-ONLY-TESTS.md): compare with one quiet run (`-n 1 -j 1 -T 8 -l 0`) first; only the difference is a load flake.
* A test that fails in some runs is a race in the test: find the pattern in the table above and apply its cure.
* Do not run it on the host that is running the release gate; on Linux run it only when the gate is idle. The burners and test processes are always stopped when the script ends. Logs stay in `HUNT_OUT` when something failed.

## What the audit counts, and what stays risky
`dist/scripts/flaky-patterns.py` is a heuristic scanner, not a proof: a hit is `ok` when its surroundings show the guard (a wall-clock deadline, a condition-polling `while`, a lock, a claimed port) and `risky` otherwise. What stays risky after the conversion, and why:

* real-time audio: cured 2026-11-19 (see "The mixer on a manual clock" below); `mixer::retried_under_load` is gone (see "Last three non-deterministic groups" below);
* product time semantics that read the wall clock (jobs "quiet" detection, IDE once-a-second refresh, ...): they need a clock injected into the product code first;
* tests of "nothing happens" (a negative check needs a quiet window, not a wait);
* JavaScript and Chrome tests (`crates/iyakki-remote/tests/*chrome*.rs`): the sleeps are in the page script, not in Rust;
* fixed delays inside fake servers (`Site::new(40)`): they model latency, nobody waits for them;
* `set_var` of a variable only that test reads (unique names): harmless, listed until it carries `// flaky-ok`.

## What the first hunts found (2026-11-18, two Apple Silicon Macs under load)
Real races in the tests, now cured; each one is a member of the classes above.
* sshfs `testdir::alive` judged every other process dead without `/proc` (macOS) and swept the folders of a test run that was still going: `sftp_tests::*`, `extagent` and other "NotFound" failures. The agent's copy had the guard already.
* The `childgone` tests took a child's exit status "from behind" while a `sleep 1.5` stub lived: a loaded machine started the thief too late. The stub now waits for a gate the thief opens when it has found the child; a scenario in which the code under test reaped the child first is run again.
* `k3sdev` alert, `domains` listener answer, extagent login cancel (child id file), IDE redraw counting, `preload_tests` (14 fixed sleeps), jobs log cap, `flows` browser retry: fixed sleeps or attempt counts replaced by waits on the thing itself.
* Model calls held open by the test (board stop, autopilot switch-off) instead of "takes 300 ms, so the switch lands inside".
* Fixed ports behind the `FIXED_PORT` lock (browsertools); camera refusal "at once" asserted by what was not called, not by a stopwatch; clientlink lock test asserts order instead of elapsed time.
* About 180 polling loops `for _ in 0..N { ...; sleep }` became wall-clock loops (30 s or more); small `wait_for(secs)` helpers have a floor of 30 s.

Seen under load and NOT fixed (reason): `sshfs ssh_server::...never_opens_its_window` (the client sends 2000 packets as fast as it can; the bound depends on how fast the server thread runs: needs a paced client or a counter in the server), `proxy guard::..swallows_packets` (partly fixed: the accept queue of macOS), `extagent::login` ("could not open a terminal": the Mac runs out of ptys when 8 runs open them together; use `-j 2` for that crate), the `iyakki-netscan` mDNSResponder test (needs a real network), and the Linux-only `jobs`/`gitjobs` tests (they read `/proc`; run the hunt for them on Linux when the gate is idle). Hunting the `iyakki-apps` crate as a whole took more than 30 minutes per run on a shared Mac, so it was hunted by filter (the tests changed here); the whole-crate hunt belongs on Linux.

## Hunt of 2026-11-19 (iyakki-agent and iyakki-proxy on the Linux build host, load average above 100)
Cured, each with its cause:
* `tenantconfig::localchat_tests::tcfg_local_chat_holds_the_fair_share_slot_while_the_host_answers`: the fake host held the first call for a fixed 2.5 s while the second call waited a 1 s queue limit; a loaded machine started the second call too late. The host now answers only when the test opens a gate.
* `settingstools_backup_more::share_system_and_chain_backups_...` and `settingstools_tests::backup_tools_...`: the tools find the person's home through `$HOME`, so the tests created, deleted and listed folders (`b`, `Documents`, `backups`) in the REAL home of whoever ran them, shared by every parallel run ("write failed: No such file"). They now run with `HOME` set to their own rig folder under `iyakki_testkit::EnvGuard` (the env lock).
* the real-Chrome web UI test: the page script waited 20 s for a tile to come alive; the budget is 120 s now.
* `audiosink::only_the_entry_point_knows_about_the_mixer_setting` (camsource read the mixer setting directly) and the media group list of the quick-install test (the browser add-on item): not load flakes, plain failures after merges, repaired.
Do not run a hunt with the same `TMPDIR` as an `rcargo` build: rcargo deletes its scratch folder after every run, and the hunt's tests then fail with "No such file" (a false flake pattern: profile, tasks, testdir, localchat). Give the hunt its own `TMPDIR`.

Seen under that load and first NOT fixed: `embedmedia_tests` (stream and mp3 pitch/length) and `mixer::stress_tests` (the mixer thread played in real time, a starved thread left gaps in what the fake card heard). Both are fixed now: the mixer runs on a manual clock, see "The mixer on a manual clock" below.

## Hunt of 2026-11-19, iyakki-apps (a full run of the unit tests, two at a time, 16 threads each, burners next to them)
* Eleven `settings_keyboard_tests` and the input tests waited on ONE cross-process `input-state` lock and timed out after 120 s. Cure: the lock for in-process statics is `process_lock` (no other process waits, 15 minutes), and the Keyboard page tests no longer write the process-wide input layer unless they ask for it (`live_input()`); 15 of 24 need no lock at all now.
* `a_script_that_sends_the_page_on...`: a REAL bug. The live page the browser keeps after a load reported the navigation the loader had already followed a second time, with its first update, and the browser followed it without the hop limit and the same-page check, at a moment that depended on the speed of the machine (a stray hop to `/c5`, or to `/self#again`). `run_page_live` now takes the load-time request away from the live engine.
* `starting_a_run_does_not_wait_for_the_context`: asserted 60 ms of wall time; now CPU time of the UI thread.
* `stop_ends_the_job_without_blocking...`: `sleep 300 ms` for the trap and `elapsed < 500 ms`; now a gate file and "the click came back while the job still runs".
* `tales_picture_that_is_slow...`, `tales_picture_stops_after_the_time_limit...`: the fake picture server answered after 900 ms / 1200 ms; now it answers when the test opens the gate.
* `panels_that_fail_the_same_way...`: the address is rewritten before the audit line is written; the test waits for both. `pull_all_asks_before...`: the real status read that follows a finished fetch overwrote the state the test had set; setting it drops the read on its way and the test sets it again after the fetch. `publish_from_the_ide_end_to_end...`: presses the header button again until the form opens. `a_run_lights_the_graph...`: draws until the Approve and Reject buttons are there. `a_login_starts_the_client_on_a_terminal...`: no draw (which fits the terminal to the tile) before the program has printed the size it started with.
* `chat_reachability_gate` (not a load flake): the Alexa page had no row in CHAT-REACHABILITY.md.

## The mixer on a manual clock (2026-11-19)
`Mixer::start_with_clock(cfg, sink, MixClock::manual())` (crates/iyakki-agent/src/mixer/clock.rs). The product uses `Mixer::start` (the real clock, unchanged). On a manual clock the mixer thread mixes only the periods the test lets pass: `mixer.advance(d)` moves time and returns when the thread has mixed everything that time covers and is asleep again (`settle()` after a write or an open). A step of one period (`20 ms`) is a thread that is always on time, a larger step is a stall of that length (the 100 ms stall tests). Everything the mixer measures runs on that clock: the card's timeline and the lead, the heard position of a source (`played_ms`), the open retry, `write_i16_wait` and `finish_and_wait` timeouts, and with `Tap::start_with_clock` the web sound tap's quiet spells. A test asserts what was mixed (a gap in what the card heard, the underrun counters, the heard position), never how fast a thread ran, so a starved machine cannot change the result.
* `FakeSink::with_clock(&clock)` stamps its writes with the manual time; the card of `mixer/stress_tests` hears gaps by that time.
* Threads that feed the mixer on their own (the player of `embedmedia`, the web sound tap) are not on the clock: the test lets a period pass only when every sound that plays has audio queued (`Mixer::feed_state`, `Rig::tick` in `embedmedia_tests`), and for the tap only when it is quiet (`Tap::busy`). A player's picture follows `pos_ms`, which the player thread refreshes: `Rig::settle_player` waits for it (two `turns`) before a picture is read.
* One test of the real clock stays: `mixer::stress_tests::the_real_clock_mixes_a_finished_source_to_the_end` (the thread paces itself on the wall clock; only the outcome is asserted, with the 30 s budget).
* The fake web engine helper that several `iyakki-apps` tests start is found and built by `apps::tests::fake_webview_binary()`: it works out the target folder and profile from the test program's own place, so the program may be started by cargo, from its path (flake hunts) or by a debugger.

## Gate flake of 2026-11-19 (apps::voice)
* `pasted_text_is_read_with_kokoro_...`: asserted `is_reading()` right after the Play click, but the fake speaker "played" for 0 ms, so on a loaded machine the reading thread had already finished (found by the hunter in 2 of 30 runs). The test now uses a `GatedSink` whose sounds play until the test opens the gate. The voice `wait` helper counted 1500 ticks (about 15 s) instead of a wall-clock budget (now 120 s), the upstream timeout of the fake Lemonade is 60 s, and `the_keyboard_reaches_everything` held its sounds 300 ms while pausing (now 60 s, every reading in it is ended by Esc or stop).

## Last three non-deterministic groups (2026-11-19)
* `radio_real_http_tests` (Opus, and Ogg): the retry (`retried_under_load`) hid a REAL bug, not a starved thread. The decoder pipe (`aacpipe::PipeDecoder::read`) handed out whatever bytes the helper had written when the reader looked; the helper's standard output is line buffered, so a write can end in the middle of a sample, and a read of an odd number of stereo samples made the radio drop one sample (`n - n % channels`): left and right swapped for the rest of the stream (gain 0.147 / 0.184 and about -12 dB in the hunt). `read` now hands out whole frames only and keeps the rest for the next call (test `a_frame_cut_in_two_by_the_pipe_is_never_handed_out_in_halves`). The tests also waited with a 40 s loop that a loaded machine overran; they wait with the testkit budget now and say what the player was doing when it does not get there. `mixer::retried_under_load` was removed.
* `clientmedia::a_hung_connection_that_stops_pulling...`: the liveness window (40 ms in the test, 4 s in the product) was read from the wall clock. `AudioRoutes::with_clock(alive, now)` takes the time source (`with_alive` and `new` keep the real clock); the test moves a `ManualClock` and asserts the edge (alive exactly at the window, silent one millisecond later).
* `cameras_tests` "frames in half a second": the picture-rate cap (`SMALL_FPS` per second) and the dark watch read the wall clock in the stream thread. `Hub::set_clock` (tests only) gives the stream a clock; the test lets a fifth of a second pass per step, waits until the camera has delivered at least five more pictures (`Hub::pictures_read`) and asserts that the cap kept all of them back while the clock stood still, then that exactly one more was kept per step.
* Other tests with a wall-clock bound under about a second, cured the same way: `assistrun_tests::independent_read_only_calls_run_at_the_same_time...` (each call waits until four are running together, no stopwatch), `iyakki-js` `blocking_scripts_run_first...` (a fetch is held until another one runs with it), `iyakki-core` `a_probe_still_stuck_is_not_started_twice...` (a one-hour wait instead of a 1 s stopwatch), `iyakki-apps` `the_background_scan_never_makes_the_caller_wait...` (CPU time of the calling thread).
* Not changed (bounds of a second or more that are not a window of the product but a guard against a hang, or need the product to take a clock first): `dash_tests` slow cluster (1100 ms), `settings_enchome_tests` move (1000 ms), `assistrun_tests` latency breakdown (`tools < 400`, `overhead < 400`: these assert the product's own timing report), the `iyakki-link`/`iyakki-sshfs` fuzz and hang guards (5 to 7 s).

## Three more apps flakes (2026-11-19, a full apps run with about ten agents building on the host)
Three tests failed in a parallel run and passed with `--test-threads=1`. Causes and cures:
* `settings::sound_tests::the_highlight_timing_offset_is_an_advanced_row...`: the offset is ONE value per process (`audiosink::HIGHLIGHT_OFFSET_MS`) and `update_sound_in` wrote the value of the sound settings into it on EVERY sound change, so any other test that changed the volume, the mute or the mixer (each with its own settings store, offset 0) wrote 0 over the -50 the test had just set, and "the agent applied it" failed. The turn lock of the three offset tests could not help: the writers were all the other sound tests. Cure in the product, which is also the right semantics: the offset is applied when it CHANGES (`update_sound_in` compares before and after); the saved value is applied at boot by `audioout::install`. `apply_prefs` no longer touches it.
* `story::tests::tales_picture_that_is_slow...`: the fake server was gated, but the log line "waiting ..." is written every 100 ms from the first moment the picture is working, and the first one can be written before the first answer of the health call arrived (a slow thread on a loaded machine), so it had no server state. The test now waits for a waiting line that carries the server state (the log repeats the line) and checks that every waiting line names the model.
* `voice::tests::a_remote_voice_asks_first...`: "the machine is not really there": the speech call to `lemon.lan` failed after a DNS lookup, so on a fast moment the reading had already ended before `is_reading()` was asserted (and the closing check could not see the reading either: the fake server never gets the call). The test now puts the network behind `HeldRemote`: calls to a `.lan` machine wait for a gate (opened when the test ends, also when it fails) and then fail, so the reading stays on until the test ends it.
* `story::...a_long_story_with_a_big_picture_is_cheap...` (found by the whole run): compared wall time of a whole frame with wall time of an animation frame; both are stretched by the load by different amounts. Both are measured in CPU time of the drawing thread now.
* `camera::live::...a_recording_is_a_playable_avi` (whole run): asserted `fps > 1` of the header, which is frames over the real length of the recording (a starved camera thread: 4 frames in 7 s, 0.57). The arithmetic is now a function (`part_fps`) with an exact test; the file test asserts the header holds a rate the writer accepts.
* `chat::chain_tests::a_voice_session_has_the_tools_the_chat_chain_gives...` (whole run): both chain tests used the REAL home (`$HOME`, `~/Dashboards`), where the other one leaves a "last opened" marker; the voice session then had five dashboard tools the chat chain of the test did not. Each now sets `HOME` to its own folder under `EnvGuard`.
* `story::...browser_at_every_screen_size` (whole run): the fake browser page ended a piece after 1200 ms of wall time; a loaded machine took longer between the Play click and the Pause click, the reading was done, and the Pause click started it again (Buffering). The page holds a started piece until the test lets it end.
* `cameras::...the_sign_stops_it` (whole run): a REAL race in the recorder. A supervision step (`Recorder::tick`, every two seconds on its thread) reads the settings first and acts afterwards; a change to "off" whose own step ran in between left the stale step starting the recorder again, so a recording the person had just stopped through the red sign ran on for up to two seconds. Steps now run one at a time (`tick_lock`).

## Gate flake of 2026-11-20 (apps::settings::browserheaders_tests)
* `apply_hands_the_header_to_the_transport_only_for_matching_sites`: the rules the transport reads (`iyakki_agent::browserheaders::ACTIVE`) are ONE set per process, and `browser_headers::apply` replaces them whenever another person's rule file is another text. Every other test that loads a page in the Browser calls `apply` for its own person (no rules) and wrote an empty set between the test's `apply` and its read of the provider. Cure: `browser_headers::Pin::to(&cx)` (tests only) takes the process lock `names::BROWSER_HEADERS` and makes every other person's `apply` a no-op while it lives; the six header tests hold it, and so do the three agent tests that activate rules.
* `iyakki_testkit::lock(names::ENV)` and `names::CWD` are in-process locks now: an environment and a current folder belong to one process, and four runs of a hunt at once starved each other on the 120 s file lock (`browserdevices_tests::hidden_devices_...` timed out).
* Seen by a hunt filtered on `browser` and NOT fixed (outside this file): `browser::a11y_tests::forced_colours_use_the_os_palette...` (the visited-link colour differs in 2 of 30 runs), `ide_tests::browser_tests::the_assistant_opens_the_page_in_the_ide_and_the_person_watches_and_can_take_over` ("a click by the person takes over", 2 of 30), `browser::tests::installed_sites_are_on_the_start_page_...` (`current_url` None after `open_item`, 1 of 30).
