# Accessibility

What works today for a person who cannot see the screen well, or cannot use a mouse, and what does not. Read the last part before you
rely on any of it: **no screen reader user has tried this yet.** Everything below was exercised only through tests with a fake voice and
a fake keyboard (see "How it was checked").

## Turn it on without seeing the screen

Press **Super+Alt+S** (Super is the Windows or Command key). It works on every screen, including the sign-in screen and the lock
screen, and the choice is kept for the computer, so the next start is already speaking. It says "Screen reader on" when it has a
voice. Press it again to turn the reader off.

If you cannot hold three keys at once, turn on **sticky keys** first (Settings, Accessibility, key `k`; or ask the assistant). Then
press Super, let go, press Alt, let go, press S.

The reader speaks with the reading voice of **Settings, Voice**. If no voice is set up it cannot speak, and it says so **on the
screen** (a small sign at the bottom right, and a message), because that is all it can do: a sighted helper has to open Settings, Voice
and choose a voice. This is the main gap for a first start on a new computer.

## The keys

| Key | What it does |
|---|---|
| Super+Alt+S | Screen reader on or off, anywhere |
| Super+Alt+Right (or Down) | Next control on the screen: top to bottom, left to right. A ring is drawn round it; the reader says it |
| Super+Alt+Left (or Up) | Previous control |
| Super+Alt+Enter | Press the marked control (the click a mouse would send to it) |
| Super+Alt+R | Say the last thing again |
| F1 | The keys of the screen you are on (also read aloud) |
| Tab, arrows, letters | Each screen keeps its own keys, as before |

The walk works without the screen reader too, for a person who cannot use a mouse: every control that can be clicked is a stop on it.

## What the reader says

* The control you walked to: "Save, button", "Dark mode, switch, on", "Volume, slider, 40 percent", "Network, tab, selected".
* Braille: with a USB HID braille display connected (the standard of usage page 0x41; one driver for every display that follows it), the same words the reader says are shown on the display's cells (uncontracted English braille; a password is never shown, only the count the reader speaks). Pan keys move along a long line, the up and down buttons move the focus. Off by default: Settings, Accessibility, key B, or the assistant: `braille` in `accessibility_set` (it asks first). The reader must be on too. Displays with a protocol of their own (serial, vendor) are not served; contracted braille is not built; not tried with a real display.
* A text field that took the focus, and its text: "Name, edit, Ann". Typing is read back one character at a time while Typing echo is on (Settings, Accessibility, key E, or the assistant: `typing_echo`; on by default, never for a hidden password field).
* A **password** field says "Password, password field, 5 characters typed". The characters are never given to the speech queue; the
  model that carries them keeps only the count.
* A new screen or page ("Settings, Display"), then the first control with the focus.
* The chosen row of a list when the arrow keys move it, on screens that use the toolkit's list rows.
* Toasts, the sign-in error, notices and the messages Settings pages show (switch these off with "Read messages and errors aloud").
* A new focus **interrupts** what is being said. A notice waits for what is being said and is dropped if you move on first.

## Settings, Accessibility

Open it with F7 then the page list, or search "accessibility". Everyone has it; no administrator is needed.

| Key | Choice |
|---|---|
| `r` | Screen reader (same as Super+Alt+S) |
| `t` | Test the voice (says a sentence, or says why it cannot) |
| `n` | Read messages and errors aloud |
| `c` | **High contrast**: black and white, a yellow accent, thick borders. It is the theme of Settings, Display; every text pair is at least 7 to 1 (WCAG AAA), checked by a test that computes the ratios |
| `u` / `U` | Bigger / smaller text and buttons (the UI size of Settings, Display: 85, 100, 125, 150, 200 percent) |
| `p` | Large mouse pointer (two more pixels per pixel of the pointer picture) |
| `f` | Big focus ring (twice as thick) |
| `m` | Reduce motion: no moving background or particles, a caret that does not blink |
| `k` | Sticky keys: Shift, Ctrl, Alt and Super stay on for the next key. Twice in a row keeps one on until a third press |
| `w` | Slow keys: a key counts after it was held 300, 500, 800 or 1200 ms (cycles, back to off). A brush against a key does nothing |

The delay and the speed of a held key repeating are in **Settings, Keyboard** (administrators). They were not copied here.

**By chat:** `accessibility_status` shows every choice and whether a reading voice exists (it asks nothing); `accessibility_set` changes
any of them (screen reader, notices, high contrast, large pointer, big focus ring, reduce motion, sticky keys, slow keys) and **asks
every time**. The assistant cannot hear the voice, so it says what the status shows and never claims the reader works.

Where the choices are kept: `access-<name>.json` (yours), `access-machine.json` (only "screen reader on", so the sign-in screen
knows), and the theme and size you already had in `ui-<name>.json`. The shell reads them again within a second of a change.

## For developers of tiles

The toolkit (`iyakki-uikit::access`) builds a node for every clickable region of a frame: the **visible label is the accessible
name**, the role comes from the kind of event (a key or tab id is a button, a row id an item, a field id a field), and the state is
empty. Most tiles need nothing. To say more, call `access::describe(label, &event, Meta::new(Role::Toggle, State::default().checked(on)))`
right after registering the hit (the switch, slider and text field of the toolkit already do). A tile that wants to say something that is
not a control calls `access::announce("Export finished")`. A chosen list row drawn with `fx::row_at` is noticed on its own.

## How it was checked

* Tests compute the contrast of every text colour on every ground of the three themes (WCAG ratios, not by eye) and of a real button.
* The speech queue, the node text, sticky keys, slow keys and the walk order are pure code with unit tests; the reader is driven in
  the shell with a **fake voice that records** what it was asked to say, at the sign-in screen, in a walk, on a new screen, with a
  toast, and with a password.
* A test walks the main screens (sign-in, home, lock) and **every Settings page** at two screen sizes and compares the walk with the
  list of clickable regions: nothing clickable is left out. The tests also print how many controls of each page have a key of their
  own and how many only the walk reaches.
* The key chords and sticky and slow keys are tested on raw key events, not on a physical keyboard.

## Honest gaps

* **No real screen reader user has tried it.** The wording, the speed, the order of the walk and the amount of speech are guesses.
* **Nothing has been heard on a real speaker.** The voice is the Settings, Voice reading voice; its quality and delay are those of
  that engine (a local engine that starts slowly makes the reader slow).
* **Web pages in the Browser tile are not exposed.** The reader sees the browser's own address bar and buttons, not the page. A web
  page's headings, links and forms are not spoken. (A page has its own dark and high-contrast rules; the browser tile's colours do not
  follow this theme.)
* **WebAssembly tiles and third-party tiles** that draw their own picture are walked only as far as they register clickable regions
  with labels; unlabelled regions are skipped, and a tile that draws pixels without regions is silent. A tile in a window of another
  program (a Linux app) is outside all of this.
* **Braille is not supported** (no braille display driver, no braille output).
* Typing echo says characters only (no word echo, no spell-out); text is read when a field takes the focus.
* The reader follows the focus of fields and chosen rows plus the walk. A tile that moves its own highlight without using the
  toolkit's row or field does not speak until it calls `announce` or `describe`.
* Dialogs of tiles are not announced by title yet, only the ones the shell itself owns (sign-in, lock, Help, power menu) and the messages
  Settings pages show. Other tiles' toasts are spoken because the shell's toast is.
* Volume and brightness changes show a bar and are not spoken.
* The large pointer applies on the framebuffer (a real screen). In a browser window the browser's pointer is the browser's.
* Reduced motion covers the moving backgrounds, the sign-in galaxy and the caret; some small spinners and progress animations in
  individual tiles still move.
* Slow keys also delay the volume and media keys.
* The recorded voice reads what it is given; it does not choose pitch or a different voice for roles.
* The page for narrow windows (under about 760 pixels) lists the switches in one column and may cut the last ones off; the keys
  `r n c p f m k w u` always work.

## Browser

The built-in Browser tile (the reader-style engine, `crates/iyakki-web`) now exposes the page itself, not only its address bar and
buttons. This section supersedes the gap "Web pages in the Browser tile are not exposed" above for pages shown by that engine. **No
screen reader user has tried it**; everything below was exercised with a fake voice and fake keys on three fixture pages (a shop, a
sign-in form, an article).

### What the page tells the reader

The page's tree is made when the page is: **roles** (link, button, heading with its level, list and list item "3 of 7", form field,
check box, radio button "2 of 3", drop-down, picture, table with caption, rows and columns, group, landmark: navigation, main, banner,
footer, complementary, search, a named region or form), **names** (`aria-labelledby`, `aria-label`, `label for`, a wrapping label, the
text inside, `alt`, `title`, a placeholder as the last resort) and **states** (checked, unavailable, expanded or collapsed, required,
invalid with the page's error message, read only, selected, pressed, current page). Not shown to the page's reader: `display:none`,
the `hidden` attribute, `aria-hidden="true"`, hidden inputs, a closed `details` (only its summary), pictures with `alt=""`.
Text that is only hidden by moving it off screen (the "screen reader only" trick) stays, because that is what it is for. A password
is never read back.

What is said: "Sign in, button", "Heading level 2, Pricing", "Email, edit text, required, invalid, Enter an email address with an at
sign", "Remember me, checkbox, checked", "Image, Red running shoe", "Sizes and prices, Table, 3 rows, 2 columns", "$55, column Price",
"Primary, navigation landmark". The words are made by one function (`iyakki_web::a11y::speak_node`) from the node and, for fields, the
value the person typed or chose, and handed to the operating system's screen reader above (`Role::Spoken` of the toolkit). **Nothing is
spoken unless the OS screen reader is on** (Super+Alt+S). When a page appears it says its title, the number of links, headings and
form fields, and any `role="alert"` text.

### Keys in the Browser

| Key | What it does |
|---|---|
| Tab, Shift+Tab | Next, previous link or control in page order, with a ring; `tabindex`, disabled controls and radio groups are handled like a browser does. Enter or Space presses it |
| Up, Down, Left, Right on a radio button | Choose the previous or next button of the group (they no longer go back or forward while a radio button has the focus) |
| V | **Browse mode** on or off (on by itself while the screen reader is on, see the settings below) |
| H, 1 to 6 | Next heading, next heading of that level (Shift: previous; `!` `@` `#` `$` `%` `^` for the levels backwards) |
| L, F, B, T, R, I, G | Next link, form field, button, table, landmark, list, picture (Shift: previous). Past the end it wraps and says so |
| M | Skip to the main part: the page's own "skip to content" link, else its main landmark |
| K, J, E, Z | A list of the links, headings, form fields, landmarks. Type to search (starts-with first, then contains), Up and Down choose, Enter goes there, Escape closes. The rows can be clicked |
| A | Read the article aloud (the reader view's text); A again pauses and continues; Esc stops |
| W | Read the whole page in order, menus and landmarks included |
| Ctrl+F, or `/` in browse mode | Find in the page |
| ? | Say what the page has (links, headings, landmarks, fields without a label, pictures without a description) |

In browse mode the letters above belong to the page: B, F, R, H, G no longer go back, forward, reload, home and to the address bar
(use the arrow keys for back and forward, Ctrl+L for the address bar), and capital F, B, R, T no longer start the full engine, the blocked
list, the reader view and translate. V turns it off again. A text field that has the focus takes the letters you type.

A link to `#something` on the same page moves to that place and says it. A form that breaks its own rules (an empty `required` field, an
email without an at sign, a value shorter than `minlength`, a `required` check box not checked) is **not sent**: the focus goes to the
first such field and the reader says why. A page that comes back after a send with fields marked `aria-invalid` puts the focus on the
first one and says how many there are. Pages that mark errors only with colour, or by script after the page loaded, are not understood.

### Looks

* **Text size** of Settings -> Display already scales the whole tile, the page text included; the per-site zoom (`+` `-` `0`) comes on top.
* **High contrast**: with the computer's High contrast theme (or "page colours: always" below) every colour the page chose is replaced by
  the OS palette: black ground, white text, yellow links, cyan visited links, white borders, links underlined, no backgrounds, no
  shadows. A test computes the ratios (every pair at least 7 to 1, the check refuses a palette below WCAG AA).
* **Minimum font size** (12 to 32 pixels at normal zoom; the page's body text is 16) raises smaller text.
* **Reduce motion** makes `@media (prefers-reduced-motion: reduce)` rules apply and stops animated pictures at their first frame. The
  engine has no CSS animations to stop.
* **Big focus ring** doubles the ring round the link or control that has the keyboard (forced colours do too, in the palette's yellow).

### Choices

Everything in the first list follows Settings -> Accessibility. The Browser's own choices are in `browser-a11y-<name>.json` and are
changed by the assistant: `browser_accessibility_status` (free; shows them and what the page in the tab has) and `browser_a11y_set`
(asks every time): browse mode (true, false, "follow" the screen reader), forced colours ("follow" the computer's High contrast, "always",
"never"), minimum font size, stop animations (true, false, "follow" Reduce motion). The OS choices are still changed with
`accessibility_set`; there is no second copy of them.

### What is not covered

* **Pages shown by the full web engine (F, WPE/WebKit)** are a picture drawn by a helper program: the tile exposes only its own bar
  and buttons. The helper (`dist/webview/wpe-helper/helper.c`) draws offscreen and passes frames, input and a title; it does not hand over
  the page's accessibility tree, so a screen reader hears nothing of such a page. A sighted helper sees the page and the OS text size
  does not reach it.
* The tree is built once, when the page loaded. The engine runs a page's scripts once for sites you allowed and keeps no live page after
  that, so content a script adds later, live regions that change, and errors a script shows after a click are not announced.
  `aria-live` text present at load is said once.
* Canvas, SVG pictures (even with `role="img"`), video and audio controls, iframes and plug-ins have no tree nodes. Pictures of text are read as their `alt` only.
* A `div` with only `tabindex` and no role, and custom widgets (tabs, menus, trees) without a role, are not stops. `role="button"`,
  `link`, `checkbox`, `radio`, `textbox`, `heading`, `img`, `list`, `listitem`, `tab`, `option` and `menuitem` are understood, and
  a `summary` is a stop that can be spoken but not opened (the page shows a closed `details` without its content).
* "Visited" is spoken nowhere; visited links differ only by colour in forced-colours mode.
* The ring round a heading, landmark or table is found by matching its words on the drawn page; repeated words are matched in order, but
  a page whose words are split by images or formatting oddly may get the ring a little off. What is said is always right; where the ring
  is drawn is a best effort.
* The pacing of "read page" is an estimate (about 15 characters a second), not the true end of each sentence; very slow voices fall behind
  and the reader queues up to eight sentences.
* Touch scrolling, pinch zoom and the on-screen keyboard (the rest of F-BROW-38) are not part of this.

## Accounts, roles and policy

The first start asks for the first administrator (name: lowercase letters, digits, `-`, `_`; password 8+ characters).
Passwords are hashed with Argon2. After 3 wrong tries for a name, sign-in is delayed (1, 2, 4... up to 60 seconds).
Without a screen (containers) create accounts on the command line:

```
echo 'a long password' | iyakki user add alice --role operator --password-stdin
iyakki user add admin --role admin --if-missing --password-file /secret/password
iyakki user list
```

Passwords are never accepted as arguments. `IYAKKI_USERS=/path/users.json` points the command at another account file;
the default is `/var/lib/iyakki/users.json`.

**Roles** (templates in `crates/iyakki-sec/src/policy.rs`):

| Role | Tiles | Terminal | Files read / write | Network hosts | Agent budget |
|---|---|---|---|---|---|
| admin | all (USERS, SETTINGS...) | full | `/` | any | large |
| operator | all except USERS | full | `{home}`, `/shared` | any | large |
| user | no USERS, MESH, NET SCAN | restricted | read `{home}`, `/shared`; write `{home}` | any | standard |
| guest | CHAT, INBOX | none | none | none | tiny |

Only admins manage users and system settings; an override can never give a non-admin that power. Budgets are presets (tiny 20k
tokens, small 60k, standard 200k, large 1M, unlimited).

**USERS tile** (admins): select a person, then keys: `n` new, `d` delete (the last admin cannot be removed), `r` cycle role,
`p` reset password (resets their personal vault too), `1-4` toggle CHAT, RAG, MCP, CLI, `a` agent, `v` voice, `k` skills,
`b` budget preset, `w` browser agent (off, read-only, interactive), `f` fuel, `m` memory, `q` disk quota, `h` allowed network
hosts (comma list, `*` = all), `s` allowed MCP servers, `l` audit log. Every change is audited.

**File scopes** are part of the policy (`fs_read` / `fs_write`; `{home}` is `/home/<user>`). The USERS tile does not edit
them in this build; to narrow or widen them for one person, stop IYAKKI and add `"overrides": {"fs_read": [...],
"fs_write": [...]}` to that account in `users.json` (the file is mode 0600). Overrides refine the role template and cannot
escalate. Window mode confines host files to the host home folder ([`HOST-FILES.md`](HOST-FILES.md)).

The assistant always runs with its person's policy; risky tools ask first ([`USER-GUIDE.md`](USER-GUIDE.md#approvals-ask-first-auto-approve-safe-autopilot)).

## The vault and credentials

* Secrets live in encrypted vault files: the **system vault** (`<data>/vault/system.afv`, shared by admins, holds provider API keys)
  and one **personal vault** per account (`<data>/vault/users/<name>.afv`). Encryption is XChaCha20-Poly1305 with a random data
  key wrapped per key slot with Argon2id; a personal vault opens with the login password, so resetting someone's password
  resets their personal vault (the admin cannot read it). The `.afv` extension is a historical file name.
* Settings and tools hold only **references**: `vault:NAME`, `uvault:NAME`, `env:NAME`, `file:/abs/path`, or an external
  provider (`ext:ALIAS/path#field`, HashiCorp Vault/OpenBao, 1Password Connect: Settings -> Secret providers).
* The assistant never asks for a secret in the chat: it calls `vault_request`, which opens a masked form that stores the
  value in your vault and tells the assistant only the reference. A pasted key-like string is not sent to the model.
* If sign-in cannot open the vault the person is told (and an INBOX warning is added); model keys stay unavailable until an
  admin with a key slot signs in.
* Rules: never put keys in `ai.conf` or `mcp.json` literally; use references. Keep a backup of the vault files separate from
  the passwords. Lost password = lost vault (there is no recovery key).

## Models and providers

Settings -> Voice (`s v c m p t y`): the engines found on the computer with their voices and why an engine cannot be used, the engine, voice and speed choosers, a Test button, Re-check, and the **browser voice helper** for the window ([`VOICE.md`](VOICE.md)). Reading aloud needs no setup when an engine is already installed; the speech engines are not shipped in the images (GPL).

Settings -> Models (`a` add, `e` edit, `d` delete, `t` test, `m` chat model, `b` embeddings model, `k` key, `x` on/off,
`c` test chat). Kinds: Ollama, OpenAI, OpenRouter, Anthropic Claude, Google Gemini, OpenAI-compatible (any server that
speaks the OpenAI chat API; address required). Cloud kinds need a key (stored in the vault). NET SCAN adds an Ollama it
finds in one step. Older `ai.conf` `chat.url` / `chat.model` lines are migrated to a provider named `legacy`. Token usage is charted in
USAGE (the provider's own counts when reported, otherwise about four characters per token). Ollama can be installed and
started from the CLI tile (listens on 127.0.0.1 only, models under the data folder).

**The provider's own model list and per-model request options.** On a selected provider, **List models** (`L`; `E` for an
embeddings model) asks the provider for its list (`GET {address}/models`, with the key from the vault; the key is never shown),
opens a chooser with a search box, and saves the pick exactly as `m` does. The list is kept for the session. If the current model
is not in a list that was fetched, the page says so in plain words ("The model X is not offered by this provider for this key").
**Options** (`o`) shows one row per request option of the chat model: `max_tokens` (1 to 1,000,000), `temperature` (0 to 2),
`top_p` (0 to 1) and `reasoning_budget` (tokens the model may think with; 0 is off). They are kept per `provider/model` in
`model-options.json` (versioned; a damaged file is moved aside, a newer one is left alone) and an option is sent only when it is
set. `reasoning_budget` is sent to NVIDIA NIM only (its API takes `reasoning_budget`); for the others the row says "not used by
this provider". Gemini gets none of the options yet. A reply that carries only thinking (`reasoning_content`, `reasoning`) is
never shown as the answer, is not read aloud, and ends with one plain sentence; reasoning tokens are counted where the provider
reports them. The assistant has `models_list` and `model_options_get` (free) and `model_options_set` and `provider_models_fetch`
(each asks every time, with the old and new values, or the host that gets the key, on the card).

## The audit log and its hash chain

Every sign-in, app open, denied action, account change, tool decision, screenshot and installs is appended to `audit.log`
(`/var/lib/iyakki/audit.log`; window mode `~/.local/share/iyakki-dev/audit.log`; mode 0600). Each line is JSON with `ts`, `user`,
`event`, `detail`, `prev` and `hash`, where `hash` is the SHA-256 of `ts|user|event|detail|prev` and `prev` is the previous line's
hash (64 zeros for the first). Every append takes an exclusive file lock (`flock`) on `audit.log`, re-reads the last line under it, writes the line and flushes it to disk before letting go, so the shell, the core and the command line can write at the same time without two lines sharing a `prev`; a line cut short by a power loss is skipped and the next line chains to the last whole one. **Verify in the app:** USERS -> `l` shows "Audit log - chain intact (N entries)" or "BROKEN at entry I".
**Verify outside IYAKKI** (any machine with Python 3):

```python
import hashlib, json, sys
prev, n = "0" * 64, 0
for i, line in enumerate(open(sys.argv[1], encoding="utf-8")):
    if line.strip():
        e = json.loads(line)
        h = hashlib.sha256(f'{e["ts"]}|{e["user"]}|{e["event"]}|{e["detail"]}|{e["prev"]}'.encode()).hexdigest()
        if e["prev"] != prev or h != e["hash"]:
            sys.exit(f"BROKEN at entry {i}")
        prev = e["hash"]; n += 1
print(f"intact ({n} entries)")
```

A clock that is corrected while the system runs (the network time arrives about 30 s after boot on a computer with no usable hardware clock, or the clock floor lifts it at the start) does not break the chain: `ts` is part of the hashed text, not an ordering the check relies on, so two neighbouring entries may show a big step (or, after a manual set-back, a step backwards) in `ts` and still verify. Entries before the first correction carry the floor time (`docs/K3S-DEV.md`, "The clock at boot").

### What a BROKEN report means now

* **Fixed for one process.** Inside one running IYAKKI (the window, the console shell or `iyakki web`), every write takes a lock: it reads the
  last hash and appends in one step, so two events in the same second can no longer share a `prev`. The old race ("BROKEN at entry N
  but nobody touched it") should not appear in a log that was written only by fixed versions.
* **Old chains.** A chain that already contains the race stays BROKEN at that entry for good: the code never rewrites or repairs
  `audit.log` (that would defeat the point); you start a new one (below). Several IYAKKI processes on one data folder (a window and
  `iyakki web`, a script and a shell) now share one exclusive file lock (`flock`) on `audit.log`, so they no longer collide.
* **How to read the report.** "BROKEN at entry I" counts from 0. Look at lines I-1 and I of `audit.log`. If both have the **same `prev`** and
  timestamps within a second or two, it is the old race (or two processes); the entries themselves are fine. If a line was edited, removed or
  reordered, `hash` or `prev` no longer matches and nothing explains it by timing: treat that as tampering, keep a copy of the file, and
  check who had access to the data folder. The chain proves order and integrity, not who wrote it from outside IYAKKI.
* **Starting a new chain.** In USERS, open the audit log (`l`) and press a capital `N` while it reads BROKEN: the old file is kept beside it as
  `audit.log.broken-<time>` (never deleted) and the new chain begins with an `audit.restart` line that names it. By hand, the same is:
  sign everyone out and stop IYAKKI, then **move** `audit.log` aside (do not delete it; it is your evidence) with
  `mv /var/lib/iyakki/audit.log /var/lib/iyakki/audit.log.broken-$(date +%F)` (window mode:
  `~/.local/share/iyakki-dev/audit.log`), and start IYAKKI. With no file the next event begins a fresh chain (the first line has 64 zeros as
  `prev`) and USERS -> `l` shows "chain intact" again. Keep the old file off the machine with your backups; it still verifies up to the
  broken entry with the script above. The first entry of the new log is a normal sign-in, so note in your own records why the log was
  restarted.

Run records (RUNS) use a separate ledger and `iyakki ledger-verify FILE`.

## Models and providers

Settings -> Models (`a` add, `e` edit, `d` delete, `t` test, `m` chat model, `b` embeddings model, `k` key, `x` on/off,
`c` test chat). Kinds: Ollama, OpenAI, OpenRouter, Anthropic Claude, Google Gemini, OpenAI-compatible (any server that
speaks the OpenAI chat API; address required). Cloud kinds need a key (stored in the vault). NET SCAN adds an Ollama it
finds in one step. Older `ai.conf` `chat.url` / `chat.model` lines are migrated to a provider named `legacy`. Token usage is charted in
USAGE (the provider's own counts when reported, otherwise about four characters per token). Ollama can be installed and
started from the CLI tile (listens on 127.0.0.1 only, models under the data folder).

### Lemonade (AMD Ryzen AI)

[Lemonade Server](https://github.com/lemonade-sdk/lemonade) is AMD's local OpenAI-compatible server for Ryzen AI machines (NPU,
iGPU, CPU). It serves chat models and also picture models (Stable Diffusion: SD-Turbo, SDXL), whisper (speech-to-text) and Kokoro
(text-to-speech). IYAKKI has a provider type **Lemonade** for it.

* **Finding it.** At an administrator's sign-in, and with **Detect** (`f`) on Settings -> Models, IYAKKI asks this machine's
  Lemonade ports (13305, the default since Lemonade v10.1.0, then 8000, the default before) for `GET /api/v1/health`, with short
  timeouts, together with Ollama's 11434. A Lemonade that answers is added as **lemonade-local** with its address
  (`http://127.0.0.1:13305/api/v1`) and the page says "Lemonade found at ... (version ...)". A provider that already points at that
  server is never changed, and neither is one named lemonade-local that points elsewhere (the new one is then
  `lemonade-local-<port>`). NET SCAN recognises Lemonade on the network by the same health answer (the same administrator consent
  as Ollama) and adds it as a Lemonade provider.
* **Add form.** The Type choice has **Lemonade** (default address `http://localhost:13305/api/v1`) and **Auto-detect (Ollama,
  Lemonade or OpenAI-compatible)**: give the address of any server and IYAKKI asks it (GET requests only) what it is, then saves it
  with the right type and address. A key typed in the form is used for the questions and stored in the vault (Lemonade only needs
  one when it was started with `LEMONADE_API_KEY`).
* **Models by type.** Lemonade's model list (`/api/v1/models?show_all=true`) labels each model; IYAKKI sorts them into Chat,
  Vision, Embeddings, Reranking, Image, Speech-to-text, Text-to-speech and **Video: none (Lemonade has no video models; no video
  endpoint exists in Lemonade today)**. Choose the Lemonade provider on Settings -> Models to see the sections, with each model's
  state (loaded, available, or not downloaded with its size). Only downloaded chat and vision models appear in the chat model
  pickers; vision models are also marked as able to see pictures (the FLOWS screenshot-to-model step accepts them).
* **Use for...** Click a model (or `l` for the full list) and choose what fits its type: *Use as chat model*, *Use for embeddings
  (RAG)*, *Use as TALES picture model* (your own TALES preference), *Use as reading voice...* (a Kokoro voice; TALES and chat
  replies are then read with it), *Use as speech-to-text*.
* **Load and Pull.** Lemonade loads a model by itself on its first use. *Load into memory...* and *Pull (download ...)* ask first on
  a card naming the model, its size and the server; nothing is downloaded silently. A pull shows its progress on the page.
* **Pictures.** `generate_image` and TALES call Lemonade's `/api/v1/images/generations` at the model's own size and steps
  (SD-Turbo 512x512 in 4 steps, SDXL 1024x1024 in 20) and keep the PNG only after the usual magic-byte and decode checks. SDXL on a
  CPU can take minutes; the request waits up to the generation timeout (5 minutes).

## External agents (Claude Code, Copilot)

Settings -> Agents (`d` detect, `i` install, `l` sign in, `k` API key, `m` model, `a` Auto, `u` use for new chats, `t` test,
`n` custom command). IYAKKI starts the vendor's own program, never touches the vendor's login, passes an API key only as one
environment variable read from the vault, and routes the agent's tool calls through the same approvals via a per-run socket.
Claude Code can drive Autopilot; Copilot and custom commands run as read-only advisors. Auto for an agent is off until you allow
it. **Read the terms-of-service notes before offering this to other people:**
[`EXTERNAL-AGENTS.md`](EXTERNAL-AGENTS.md#terms-of-service-decision-for-the-owner) (do not bundle the vendor binary in an image;
subscription limits assume individual use). No live run against the real vendor programs has been made yet.

## The audit log and its hash chain

Every sign-in, app open, denied action, account change, tool decision, screenshot and installs is appended to `audit.log`
(`/var/lib/iyakki/audit.log`; window mode `~/.local/share/iyakki-dev/audit.log`; mode 0600). Each line is JSON with `ts`, `user`,
`event`, `detail`, `prev` and `hash`, where `hash` is the SHA-256 of `ts|user|event|detail|prev` and `prev` is the previous line's
hash (64 zeros for the first). **Verify in the app:** USERS -> `l` shows "Audit log - chain intact (N entries)" or "BROKEN at entry I".
**Verify outside IYAKKI** (any machine with Python 3):

```python
import hashlib, json, sys
prev, n = "0" * 64, 0
for i, line in enumerate(open(sys.argv[1], encoding="utf-8")):
    if line.strip():
        e = json.loads(line)
        h = hashlib.sha256(f'{e["ts"]}|{e["user"]}|{e["event"]}|{e["detail"]}|{e["prev"]}'.encode()).hexdigest()
        if e["prev"] != prev or h != e["hash"]:
            sys.exit(f"BROKEN at entry {i}")
        prev = e["hash"]; n += 1
print(f"intact ({n} entries)")
```

> **Known alpha bug.** When two events are written in the same instant from different threads, two lines can end up with the
> same `prev`, and the verifier then reports "BROKEN" although nothing was tampered with (seen on the development machine's own
> log, at an entry written in the same second as its neighbour). A BROKEN report therefore needs a look at the lines around the
> reported entry: two lines with the same `prev` and consecutive timestamps are this race, not an attack. Run records (RUNS) use
> a separate ledger and `iyakki ledger-verify FILE`.
